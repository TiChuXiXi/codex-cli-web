# codex-cli-web：RCC（Router Communication & Control）架构升级设计与实施要求

## 一、项目背景

### 1. 现有系统

codex-cli-web 是基于 Codex App Server 的 Web 工作台，目前已逐步实现：

- Router / Worker 智能调度架构。
- Router 统一对话入口。
- 项目与历史会话自动查找。
- PSM（Project & Session Memory）项目与会话认知索引。
- Worker 派发、续接和结果回执。
- 事件驱动的 Worker 完成通知。
- 微信 iLink 接入。
- Web / 微信统一待办、审批和用户输入。
- 微信处理中反馈、正在输入状态。
- Router 人格与表达规范。

当前 Router、PSM、微信交互升级的 P0、P1、P2 均已完成开发。

但在实际使用中，发现了新的架构层面问题。

### 2. 当前问题

**问题一：Worker 执行过程中，用户补充的指令没有可靠送达。**

例如 Worker 正在执行网络配置功能，用户追加：

「测试完记得恢复自动 IP。」

Router 只是回复「已记下」，并没有真正把消息传递给 Worker。

这种情况可能发生在 Worker 正在执行、等待审批、等待用户输入或其他特殊状态时。

**问题二：Worker 完成后，后续业务要求没有正确续接。**

例如用户说：

「实际功能不需要切换网口，只需要设置手动 IPv4，不需要配置 DNS。」

Router 自己理解并记住了要求，但没有续接原 Worker。

**问题三：Router 的职责过重。**

当前 Router 可能自行理解业务要求、总结实现方案、保存任务细节，甚至把自己的记忆当作任务处理结果。

这偏离了最初的设计目标。

Router 不应该代替 Worker 进行项目业务分析、任务规划或具体实现。

**问题四：Router 难以稳定区分聊天和任务。**

例如：

「你觉得这个实现方式合理吗？」

有时是普通讨论，有时是要求正在开发的 Worker 检查代码。

仅靠模型推断容易发生漏派发或误派发。

**问题五：多个 Worker 并行时，缺少明确的消息目标和对话焦点。**

用户可能同时让不同 Worker 执行网络配置、USB 故障排查和 Web 界面优化。

Router 需要能够将后续消息准确送到对应 Worker，而不是始终绑定最近一次派发的任务。

**问题六：错误派发后缺少及时纠正机制。**

例如用户只是普通聊天，Router 却错误派发给 Worker。

用户指出「发错了，停下」后，Router 不应该只在对话中道歉，而应该能够取消尚未执行的指令、中断正在执行的 Worker，并说明实际停止情况。

---

# 二、本次升级的根本目的

我们希望 Router 与 Worker 的关系更接近现实中的工作协调。

用户只需要对 Router 说：

「让网络配置那个任务继续。」

「USB 掉线那个任务再检查一下供电。」

「刚才的任务补充一下，不要修改 DNS。」

「Web 界面那个先停下。」

Router 应当能够自然理解用户在指哪个任务，并完成转接或控制。

**Router 的工作在指令可靠交付给调度系统后即可结束，不需要等待 Worker 执行完成。**

Worker 如何分析、规划和执行，由 Worker 自己决定。

Worker 需要审批、用户决策或任务完成时，现有事件与待办系统再将信息反馈给 Router，由 Router 通知用户。

最终形成：

用户 ↔ Router ↔ 可靠控制队列 ↔ Worker

其中 PSM 只用于定位项目和会话。

本次不增加 Router 长期业务记忆，不增加独立 Agent，不重新设计 PSM。

---

# 三、Router 的职责重新定义

## 1. Router 负责

- 普通聊天。
- 识别模式切换。
- 查询系统任务、状态和待办。
- 根据明确目标、当前焦点或 PSM 定位 Worker。
- 派发、追加、修正和撤销指令。
- 发起 Worker 中断。
- 将审批、业务问题和执行结果转达给用户。
- 对无法确定的目标进行简短澄清。

## 2. Router 不负责

- 具体项目代码开发。
- 项目业务逻辑分析与实现。
- 代替 Worker 制定执行方案。
- 保存完整任务业务上下文。
- 把用户的任务补充只写入自身上下文。
- 把 PSM 当作待执行指令队列。
- 等待 Worker 完成后才能结束当前 Router 请求。
- 自行批准 Worker 原生工具请求。
- 在未确认交付时声称 Worker 已经收到。

## 3. 必须保留的最小运行状态

Router 仍然需要由服务端维护：

- 当前交互模式。
- 各渠道当前对话焦点。
- Worker 运行状态。
- 最近派发和任务关联。
- 尚未交付的指令。
- 等待审批和用户输入的待办。
- 指令交付与执行回执。

这些是确定性的调度状态，不是大模型长期记忆。

不得因此再引入新的 Router 记忆体系。

# 四、功能一：Router 双模式

## 1. 聊天模式（Chat Mode）

聊天模式下，Router 作为普通对话助手。

规则：

- 普通问题由 Router 自己回答。
- 业务讨论由 Router 自己回答，不自动派发 Worker。
- 即使用户提出「帮我修改代码」，也不能未经模式切换就自动派发。
- 可以提示用户切换任务模式。
- 允许查询任务列表、状态和待办。
- 允许处理已有审批、业务决策和紧急停止指令。
- 允许使用 PSM 查询历史项目与会话，但查询不等于执行。

默认新用户或尚未配置模式的会话进入聊天模式。

## 2. 任务模式（Task Mode）

任务模式下，Router 的主要职责是将用户业务消息交给 Worker。

规则：

- 除模式控制、系统状态查询、待办回复和紧急控制外，业务消息默认需要转交 Worker。
- 不再由 Router 判断这条业务消息是否「值得派发」。
- 不因为用户使用疑问句就改为 Router 自己回答。
- 不因为 Worker 已完成而停止转交后续修正要求。
- 不因为 Worker 正在执行或等待审批而丢弃补充指令。
- 不因为 Router 自己理解了要求就认为任务已经处理。
- Router 不需要重新总结每条指令，优先保留用户原文。

例如：

「测试完恢复自动 IP。」

「不要配置 DNS。」

「你检查一下这个实现是否合理。」

以上在任务模式下都应该交给目标 Worker。

## 3. 自然语言模式切换

至少支持：

- 「切换聊天模式」
- 「进入任务模式」
- 「接下来我们聊聊，不要执行」
- 「开始处理任务」
- 「先别派发，我想讨论一下」

应有明确反馈。

模式切换本身不能被误转发给 Worker。

## 4. 模式持久化

模式状态应保存在服务端，重启后恢复。

Web 与微信应能够显示当前模式。

建议模式作为同一用户 Router 的共享状态，避免两个入口对是否允许自动派发产生相互矛盾的理解。

如果实现发现共享模式存在明显的跨渠道误操作风险，请在计划阶段提出并比较共享模式与渠道独立模式，不要自行改变产品语义。

# 五、功能二：多 Worker 并行与对话焦点

## 1. 多任务并行

系统应支持多个 Worker 同时执行不同任务。

例如：

- Worker A：网络配置功能。
- Worker B：USB 掉线排查。
- Worker C：Web 界面优化。

不同 Worker 的运行、审批和指令队列互不阻塞。

## 2. 对话焦点（Conversation Focus）

增加当前渠道的对话焦点。

建议结构：

- `channel`
- `projectId`
- `threadId`
- `dispatchId`（可选）
- `focusRevision`
- `updatedAt`

对话焦点表示用户当前默认正在交流哪个 Worker。

它不等于唯一正在运行的 Worker。

## 3. 目标选择优先级

优先顺序：

1. 用户明确指定项目或任务。
2. 用户明确引用最近某次派发或结果。
3. 当前渠道有效的对话焦点。
4. PSM 查询结果。
5. 用户澄清。

明确指定目标应优先于当前焦点。

例如当前焦点是网络配置，但用户说：

「USB 掉线那个任务再检查一下供电。」

应直接寻找 USB Worker。

## 4. 焦点更新

以下操作可以更新焦点：

- 用户明确切换目标。
- 用户明确向某 Worker 派发任务。
- 用户确认候选会话。
- 用户明确要求继续某历史任务。

以下操作不应自动改变焦点：

- 查看任务列表。
- 查询另一个 Worker 状态。
- Worker 自动完成通知。
- 收到审批通知。
- PSM 后台同步。
- 其他渠道的焦点变化。

Web 与微信共享任务和 Worker 状态，但可以分别维护焦点。

## 5. 焦点安全性

不能仅凭「最近执行过」就把所有消息派发给该 Worker。

当消息明确引用另一个任务时，必须重新定位。

当目标身份失效、项目授权变化或存在多个无法区分的目标时，必须询问。

对话焦点应绑定可验证的项目和 Thread 身份，不得只保存显示名称。

# 六、功能三：可靠 Worker 指令队列

这是本轮最重要的功能。

## 1. 基本原则

**先可靠记录，再尝试交付。**

任何需要转交 Worker 的业务消息，都必须先获得持久化指令身份。

不能先调用 Worker，失败后才考虑保存。

不能因为 Worker 忙碌而丢弃指令。

不能因为 Router 回合结束而丢失指令。

不能因为服务端重启而重复执行同一指令。

## 2. 复用现有架构

请优先复用：

- Router Dispatcher。
- 现有 FollowupQueue。
- RouterStore。
- Worker Hub。
- EventBus。
- Wake Scheduler。
- 微信收件箱与发送队列。

不要重新实现第二套任务调度器。

如果需要新增 Worker Control Queue，请优先作为现有 Dispatcher 的控制指令扩展。

## 3. 控制指令类型

建议至少支持：

| 类型 | 用途 |
|---|---|
| `dispatch` | 开始或续接任务 |
| `steer` | 向正在执行的 Worker 追加指令 |
| `followup` | 当前回合结束后继续处理 |
| `correct` | 修正之前的任务要求 |
| `interrupt` | 中断当前执行 |
| `cancel` | 取消尚未交付的指令 |
| `resume` | 继续历史 Worker 会话 |

这些类型可以是内部调度语义，不要求新增同名公开 API。

## 4. 指令状态

建议至少区分：

- `queued`：已持久化，等待交付。
- `delivering`：正在尝试交付。
- `delivered`：Worker App Server 已确认接收。
- `deferred`：暂时不能交付，等待恢复条件。
- `cancelled`：未交付指令已取消。
- `failed`：无法继续自动交付，需要用户处理。
- `unknown`：请求结果不确定，需要对账。

不得将 `queued` 描述成 Worker 已收到。

不得将 `delivered` 描述成 Worker 已执行完成。

## 5. Worker 正常运行时

优先尝试通过现有 Codex App Server 的 `steerTurn` 能力即时追加。

成功后标记已交付。

不得在 Turn 完成后再次将同一指令作为新 Turn 重复发送。

## 6. Worker 等待审批时

需要实际验证 App Server 在审批阻塞期间能否接受 `steerTurn`。

如果可以，直接追加。

如果不可以：

- 保留原指令。
- 标记为 `deferred`。
- 监听审批解除及 Turn 状态变化。
- 在合适时机自动继续投递。

用户不需要再次发送同一条消息。

## 7. Worker 等待用户输入时

同样优先尝试即时插话。

不能安全投递时进入延迟队列。

原生 `requestUserInput` 的回答仍走原有待办通道，不能与普通业务补充混淆。

## 8. Worker 空闲时

直接续接原 Thread，启动新的 Turn。

不要因为上一轮已完成而创建不必要的新会话。

## 9. Worker 断线或服务重启

指令应继续保存在数据库。

恢复后核对 Worker 身份、Thread 状态和投递结果。

对不确定是否已被 App Server 接收的指令，不得直接重放。

应先尝试通过原生历史、Turn 或已记录关联进行对账。

无法确认时保留 `unknown`，避免重复执行。

## 10. 每 Worker 独立顺序

同一 Worker 的普通业务指令必须保持发送顺序。

不同 Worker 可以并行。

紧急中断和撤销可以优先处理，但不能破坏同一 Worker 已提交指令的因果关系。

对于短时间连续输入的多条补充要求，可以考虑在尚未交付时合并投递，但必须保留每条原始消息及顺序，不得丢失或擅自改写语义。

# 七、功能四：错误派发的纠正与中断

## 1. 目标

当用户发现 Router 转错 Worker，必须能够立即纠正。

例如：

「刚才发错了，停下。」

「不是让你改代码，我只是问问。」

「这个应该交给 USB 那个项目。」

## 2. 不同状态的处理

### 尚未交付

直接取消对应指令。

### 已排队

取消待交付记录，确保后续不会自动发送。

### 正在执行

通过现有 Worker Hub 发起中断。

需要等待真实中断结果，不能提前声称已经停止。

### 等待审批

优先阻止错误请求继续执行。

不能通过自动批准审批来解除阻塞。

根据原生协议支持情况中断或取消。

### 已完成

不得假装可以撤销已经完成的操作。

应查询实际结果和可能产生的副作用。

### 已修改文件或外部状态

不得擅自回滚。

如需恢复，应在用户确认后交由 Worker 处理。

## 3. 纠正目标

用户说「刚才发错了」，优先关联当前渠道最近一次明确派发。

如果最近存在多个可能目标，应要求澄清。

不能误中断其他并行 Worker。

## 4. 纠正后的 Worker 上下文

如果错误指令已经进入 Worker 会话，后续应尽可能向该 Worker 传递一条明确纠正说明：

「上一条指令属于误派发，请不要继续执行该要求。以当前已确认的任务目标为准。」

这条纠正本身也必须进入可靠控制机制。

如果 Worker 已经终止且无需继续执行，不应为了发送说明而无条件重新启动 Worker；应记录纠正事实，并在该会话下一次正常续接时按需传达。

# 八、功能五：Router 模型与服务端的职责分离

## 1. Router 模型负责

- 自然语言交流。
- 识别明确任务目标。
- 通过 PSM 定位历史项目和会话。
- 在必要时询问用户。
- 发起调度和控制工具调用。
- 对 Worker 结果进行简洁转述。

## 2. 服务端负责

- 模式状态。
- 当前焦点。
- 指令持久化。
- Worker 队列。
- 实时插话。
- 延迟投递。
- 重试与恢复。
- 中断和撤销。
- 权限与身份验证。
- 交付状态。
- 事件通知与幂等。

**不能依赖 Router 模型记住哪些指令尚未交付。**

## 3. 任务模式快速路径

当任务模式已经存在有效焦点时：

- 服务端可以直接将明确的普通业务消息送入指令队列。
- 不必每次都调用 Router 模型进行业务意图分类。
- 但必须先识别模式切换、系统查询、待办回答和紧急控制操作。
- 用户明确引用其他任务时，应进入目标定位流程。
- 存在歧义时不得盲目派发。

如果无法可靠判断是否指向其他 Worker，优先使用 Router 进行目标解析。

不能为了节省模型调用而牺牲准确性。

---

# 九、功能六：PSM 的职责边界

PSM 已经实现，本轮不重新设计。

PSM 只负责：

- 项目定位。
- 历史会话查找。
- 任务主题与会话关联。
- 用户确认后的关联纠正。
- 为 Router 提供历史任务的定位证据。

PSM 不负责：

- 保存待执行指令。
- 替代 Worker 业务上下文。
- 判断 Worker 是否已完成新要求。
- 代替指令队列进行可靠投递。
- 保存 Router 的完整长期聊天记忆。

当前焦点已经确定时，不需要每条消息重新调用 PSM。

# 十、微信与 Web 交互要求

## 1. 模式显示

Web 应能清晰显示聊天模式或任务模式。

微信可通过：

「当前模式」

「切换任务模式」

「切换聊天模式」

查看或改变模式。

模式切换反馈应简洁。

## 2. 任务列表

微信发送「任务列表」时，显示当前任务。

例如：

1. 网络配置 — 等待审批
2. USB 掉线 — 执行中
3. Web 界面 — 执行中

同时显示当前微信对话焦点。

## 3. 焦点切换

支持：

「切换到 USB 那个任务。」

「接下来给 Web 界面那个会话发消息。」

「继续网络配置。」

## 4. 指令投递反馈

区分：

- 「已交给网络配置会话。」
- 「已排队，等待当前操作结束后发送。」
- 「目标不明确，需要你选一下。」
- 「还没成功送达，我会继续尝试。」
- 「已取消，未发送给 Worker。」

不能统一回复「已记下」。

## 5. 任务结果

Worker 完成后，沿用现有事件回执。

Router 可以简要总结，但不得把结果通知变成新一轮业务处理。

自动完成通知不能擅自改变当前渠道焦点。

---

# 十一、异常与并发要求

至少考虑：

- 两个 Worker 同时运行。
- 同一 Worker 连续收到多条消息。
- Worker 等待审批时收到新消息。
- Worker 等待用户输入时收到新消息。
- Worker 刚结束 Turn 时收到新消息。
- Worker 中断与指令投递同时发生。
- 微信和 Web 同时向同一 Worker 发送消息。
- 服务端在指令持久化后崩溃。
- 服务端在 App Server 接收指令后、数据库确认前崩溃。
- Worker Hub 断线和重新连接。
- 原 Worker Thread 被归档或删除。
- 项目授权变化。
- Router 主会话切换或上下文压缩。
- 微信重复消息和发送重试。
- 用户在一个渠道取消另一个渠道的指令。

所有恢复逻辑必须以持久化事实和实际 Worker 状态为依据。

# 十二、实施阶段建议

## 阶段 P0：可靠指令交付

首先解决最核心问题：

- Worker 运行时追加指令。
- 审批等待时延迟投递。
- Worker 空闲时续接。
- 指令持久化。
- 顺序与去重。
- 重启恢复。

这一阶段不必先做完整 UI。

## 阶段 P1：双模式与多任务焦点

增加：

- 聊天 / 任务模式。
- 自然语言切换。
- 多 Worker 并行目标选择。
- 渠道独立焦点。
- 任务模式快速转交。
- 微信和 Web 状态展示。

## 阶段 P2：纠正、中断与体验完善

增加：

- 错误派发撤销。
- Worker 中断。
- 纠正说明。
- 任务列表和焦点切换。
- 更准确的投递反馈。
- 复杂并发与异常恢复。

阶段顺序可根据现有代码依赖调整，但必须保证每阶段可以独立验收。

# 十三、自动化测试与验收标准

## A. 指令可靠性

1. Worker 正在执行时，连续发送三条补充指令，原 Worker 实际收到三条，顺序正确。
2. Worker 等待审批时发送补充，指令进入持久化队列；审批解除后自动交付。
3. Worker 等待用户输入时发送补充，不丢失、不误当成问题答案。
4. Worker 已完成时发送新要求，原 Thread 创建新 Turn。
5. 服务端重启后，未交付指令继续存在。
6. 投递结果未知时不会盲目重发导致重复执行。
7. 同一条微信消息重复到达时，最多创建一条逻辑指令。

## B. 双模式

8. 聊天模式下提出开发需求，不自动派发。
9. 任务模式下提出业务问题，交给 Worker 而不是 Router 自己回答。
10. 自然语言切换模式后，后续消息遵循新模式。
11. 模式切换不会错误传给 Worker。
12. 查询任务状态不触发新派发。

## C. 多 Worker

13. A、B、C 三个 Worker 同时执行，互不阻塞。
14. 当前焦点为 A，明确提到 B 的消息只交给 B。
15. 无明确目标的连续补充默认交给有效焦点。
16. Web 和微信拥有不同焦点时，不互相覆盖。
17. 查询 C 的状态不改变当前焦点 A。
18. 焦点失效或目标歧义时，不盲目派发。

## D. 纠正与中断

19. 未交付指令可以取消，之后不会发送。
20. 正在执行的错误 Worker 可以中断，并报告真实结果。
21. 同时存在多个 Worker 时，不会误中断其他任务。
22. 中断后不会未经授权自动回滚文件。
23. 已完成的错误任务不会被虚假标记为已撤销。
24. 错误指令已经进入 Worker 上下文时，纠正信息可以可靠传递或留待下一次续接。

## E. 交互与回执

25. Router 不再使用「已记下」代替真实派发。
26. Router 回复的交付状态与数据库和 Hub 状态一致。
27. Worker 完成后，微信收到实际结果。
28. Worker 审批与业务问题仍能在微信独立完成。
29. 旧 PSM、Router、微信 iLink 和 Web 功能正常。
30. Router 主会话切换、服务端重启后，模式、焦点、队列和待办恢复正常。

# 十四、必须避免的设计偏差

1. 不要新增 Router 长期记忆系统。
2. 不要让 Router 代替 Worker 处理业务。
3. 不要把 PSM 变成任务指令队列。
4. 不要为了可靠投递重新开发第二套 Dispatcher。
5. 不要让 Worker 忙碌成为丢弃消息的理由。
6. 不要让 Router 等待 Worker 完成后才结束本轮交互。
7. 不要仅凭最近一次 Worker 就盲目派发。
8. 不要把任务模式等同于绕过审批。
9. 不要将中断等同于自动回滚。
10. 不要在交付结果未知时直接重复执行。
11. 不要因为人格和提示词修改而无故重建 Router 主会话。
12. 不要为了减少模型调用而牺牲目标识别准确性。

# 十六、最终成功标准

用户进入任务模式后，可以同时管理多个 Worker。

用户可以自然地说：

「让网络配置那个任务继续。」

「USB 那个任务补充一下供电检查。」

「刚才那个不要修改 DNS。」

「Web 界面那个先停下。」

Router 不需要理解这些项目的具体实现细节，只需要准确定位目标并可靠转交。

即使 Worker 正在运行、等待审批、等待输入或暂时断线，用户指令也不会被静默丢弃。

Worker 处理完成后，Router 能及时将结果反馈给用户。

用户切换聊天模式后，可以与 Router 普通交流，而不必担心业务问题被错误派发。

**最终 Router 应该成为一个简单、自然、可靠的通信与调度中枢，而不是承担所有任务的超级执行 Agent。**
