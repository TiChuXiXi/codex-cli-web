# Router MVP

Router 是工作台内的独立对话入口。它用专用 Codex App Server 管理对话，通过受策略版本约束的动态工具检索已登记项目和会话、发起调度、查询状态和请求中断。Worker 保留自己的线程、项目上下文与原生审批。用户可在 Router 和原工作台之间切换。

## 访问和执行边界

- Web 沿用工作台实例的认证。待确认项只有在界面确认后才按保存的目标与原始文本继续。Router 可跨项目检索会话，结合用户原话、最近回合与活动时间判定目标。确认目标后直接派发。确有歧义时展示少量会话，用户可点选，也可在对话中回答；原始任务只交接一次。中断必须在界面另行确认。
- Router 和 Worker 使用各自的 App Server。Router 运行在独立的工作目录及 `CODEX_HOME`，其部署启动器通过摘要校验。专用 App Server 通过 `router/capabilities` 表明固定工具策略版本和精确名单。工作台拒绝启动未报告此策略的进程。
- 专用构建在 Codex Core 工具注册层为每个新建或恢复的会话应用白名单。其外部 JSON-RPC 入口仅允许初始化、模型列表和必要的线程回合操作。部署沙箱独立限制文件、进程和网络。
- Worker 派发保留用户原文，按线程及关联 ID 交给原生队列。新建、续接和运行中追加的普通指令只发送用户原文。工作台复核项目目录身份、线程归属与当前执行范围。已授权的可写会话可直接续接。Worker 0.169.1 和 0.170.0 均已通过队列和权限验收。已有会话的配置超过项目原授权时，可在 Router 对话中一次授权该会话的当前配置。设置变化后重新按实际授权判断。
- Router 对话会展示 Worker 的命令、文件和权限审批，以及原生问题表单。卡片上标有项目、会话和任务原文。点击后由工作台把决定回给发起请求的 Worker。Router 模型没有代答或代批工具。

## 准备和启用

1. 用临时位置取得 OpenAI Codex 的 `rust-v0.169.1` 发布源码。保留其 Apache-2.0 许可证和 notices。运行 `node scripts/prepare-router-codex.mjs /path/to/codex-rust-v0.169.1`，在该副本的 `codex-rs` 目录用 Rust 1.95.0 执行 `cargo build -p codex-cli --bin codex`。本机 GNU 链接器内存不足时，使用 Clang 驱动 Rust 工具链自带的 LLD 完成链接。发布 tarball 的 workspace 版本为 0.169.1，Cargo 会在该副本中同步锁文件内原为 0.0.0 的 workspace 版本。
2. 在部署者维护的目录放置专用构建产物 `codex-router`，用 `sha256sum codex-router > codex-router.sha256` 记录摘要。用 `install -m 0755` 安装 `scripts/router-launcher.sh`。启动器与摘要所在目录只允许可信部署者修改。
3. 提供该目录下的 `model.netns`，指向一个独立于工作台宿主的 Linux 网络命名空间。由部署网络策略仅开放所用 Codex 账号或模型提供方及必要的 DNS，隔离宿主 RPC、内网服务及其他出口。服务身份须具备进入该命名空间的授权。参考启动器在此网络命名空间内用 Bubblewrap 建立挂载与进程隔离。
4. 把专用 Codex 账号、配置和历史放在 `<stateDir>/router/codex-home`。首次登录使用同版本的原版 CLI 和专用目录，由部署者完成。启用后服务会在缺失时自动生成受限的 `config.toml`。可以按部署环境选择 provider，保留禁用插件、MCP、hooks、网页搜索和遥测的设置。启动器只挂载 Router 自己的状态、只读配置和只读工作目录。业务 SQLite 和 Worker daemon socket 所在路径不提供给 Router。
5. 在应用 JSON 里添加 `router`。示例中的模型、目录及摘要由部署者用实际值替换，工作台会在启用时查 `model/list` 并验证每个候选的推理强度。

```json
{
  "router": {
    "enabled": true,
    "launcher": "/opt/codex-router/router-launcher.sh",
    "launcherSha256": "<实际启动器的 64 位小写 SHA-256>",
    "projectRoot": "/home/xixi/projects",
    "models": [
      { "model": "gpt-6.1-terra", "effort": "high" }
    ],
    "projects": [
      {
        "id": "example",
        "name": "项目名称",
        "cwd": "/absolute/path/to/worker-project",
        "aliases": ["项目别名"],
        "sandbox": "read-only"
      }
    ]
  }
}
```

新电脑使用 `config.portable.json` 时，部署完上述 Router 运行组件后，用同一个运行账号和状态目录执行 `npm start -- --config config.portable.json --register-router-launcher /绝对路径/launch.sh`。命令自动记录启动器路径和摘要，服务下次启动时加载。已有 Codex 会话中的项目自动列出，首次使用前在面板确认项目目录。授权以只读方式保存，重启后复用。路径或目录身份变化时需重新确认。专用运行组件未安装时，普通工作台可独立使用。

Router 默认关闭；启用且省略 `models` 时默认使用 GPT-6.1 Terra（`gpt-6.1-terra`，`high`）。可在 `router.models` 中设置默认模型和思考强度，按数组顺序使用账号支持的首个组合。在 Router 输入框点击模型按钮，可以选择该账号目录中的模型和思考强度。手动选择保存在当前 Router 会话中，刷新或服务重启后恢复，也可在模型列表里选择默认模型以重新跟随配置。新设置从下一次用户消息或自动回执起生效。模型与推理强度仍须通过账号目录验证。恢复已有 Router 线程时也应用所选模型，保留会话历史。项目列表可为空。项目策略默认 `read-only`，可显式设为 `workspace-write`。新建可写 Worker 将写入限制在项目目录，禁用额外临时目录和网络访问，并由用户审批。部署者可为已授权沿用所有现有会话设置的项目显式设置 `"resumeExistingPermissions": true`，使其原有完全访问或免审批 Worker 也能直接续接。省略时保留既有授权范围，可对单个 Worker 单独授权。项目路径必须是已存在的目录，与 Router 状态目录分离。

## 任务、恢复和停用

「设置 → Worker」可调整普通工作会话与 Router 派发的默认模型、思考强度、会话权限及执行模式。权限选择「沿用项目或 Codex 配置」时，手动新建会话使用 Codex 配置，Router 新建 Worker 使用登记的项目权限。续接已有 Worker 时，省略权限即沿用它原来的权限。单独新建和新建并派发都会在原生会话创建时应用该权限。默认值超过项目授权范围时，Router 会先展示确认卡。修改默认值不影响已提交的任务。「只读」指 Codex 的原生沙箱，获批操作和外部 MCP 服务的权限由各自的机制决定。

可以说「继续库存界面任务，用 Terra、高思考、只读和计划模式先分析」。Router 会把选项随任务保存，在 Worker 空闲时调用原生会话设置接口，再用原队列交付用户原文。所请求的权限超过已授权范围时，Router 对话会展示目标与权限供用户授权。「任务」页列出每次派发的参数。

可以向 Router 查询已有 Worker 当前的会话权限、模型、思考强度和活动回合。只修改设置时，确认后等待会话空闲，再按新设置保存，保留未指定的项目。若明确要求「修改后停止并继续」，确认卡会显示更改前后配置。Router 只中断确认时的原回合，等待原生中断状态，核对新设置后在同一会话发送预设续执行提示。提示要求从未完成处继续、保留已有改动，并沿用原生审批和提问。原回合已更换、原任务自然完成或已有其他待执行消息时，Router 会停止这项续执行。

Router 标题栏的右侧面板提供本机文件、文档预览与交互终端。文件浏览以 Web 服务账号能够访问的文件系统为范围。使用 WSL 时可以展开 `/mnt/c`、`/mnt/d`，也可以在文件面板里粘贴 Windows 磁盘路径。终端由使用工作台的人操作，Router 模型仍沿用其原有的工具权限。

在「设置 → 中枢」可分别修改默认模型、思考强度和新项目父目录。父目录使用运行 Web 服务的机器上的绝对路径。安装时可用 `router.projectRoot` 预设目录；省略时，启用 Router 的工作台会在首次打开时提示设置。选择「稍后设置」后，工作台记住该选择。需要新建或克隆项目时，Router 会在对话里询问。保存目录后，等待目录的请求自动继续；取消的请求不会执行。浏览和续接已有项目无需设置目录。面板保存的设置在重启后继续生效。

可以直接对中枢说「建一个叫库存看板的项目」或给出 HTTPS Git 仓库地址要求克隆。工作台在父目录下创建独立子目录，登记到项目列表，并使用现有 Worker 会话创建和派发流程。遇到同名目录时保留原内容。也可点击侧栏搜索框右侧的「新建项目」，输入名称或仓库地址，或选择已有目录。

任务与已落盘的用户确认保存在 `stateDir/router/router.sqlite`。同一状态目录只允许一个调度实例。任务开始前写入提交意图，再交接给 Worker 的原生队列。提交结果丢失时以 `clientUserMessageId` 和原生队列 ID 对账。队列条目移出后预留回合历史可见的时间，再把缺少关联证据的任务标为待核对。未知结果暂停该线程的 Router 队列，操作者可打开相应会话核对，然后明确关闭待核对任务。关闭保留原记录和审计事件。

Router 通过 SSE 刷新任务状态和待处理请求。重新打开网页时，卡片从 Worker 当前挂起的请求恢复。工作台按任务、线程、回合和请求实例核对回复。如果当前回合创建了直接子代理，也会恢复其订阅，卡片会标出子代理名称。Worker 以结构化消息发来的异步问题沿用原表单，执行中把回答送进同一回合，回合结束后通过原队列续接该线程。

关闭浏览器后，服务仍可执行任务。需要在 Web 服务重启期间继续执行时，应让 Worker App Server 作为独立 daemon 运行并共用原来的 `codexHome`。使用 `stdio` 时，Worker 进程的生命周期跟随 Web 服务。关闭 `router.enabled` 会暂停未交接的任务并保留历史，重新启用后按原记录对账。

### Worker 自动回执

Worker 的关联回合结束时，Dispatcher 在保存终态的同一个 SQLite 事务中记录回执和标明来源的 Worker 回复。最终文本最多保留 24,000 个字符并标注截断。失败或中断会显示相应状态。Web 停机期间错过的结果会从原生回合历史恢复。同一任务的原文只记录一次。

Router 空闲时再合批生成汇报。每批最多 10 条，通常先等待 1 秒合批。自动回合间隔至少 10 秒，滚动 24 小时最多启动 60 次。等待汇报期间，用户已经可以在对话中阅读 Worker 原文。自动回合只允许通过 `get_task_status` 读取批内结果。后续派发、创建会话和中断依然由用户发起。

回执与 Worker 执行状态分别展示。已确认失败的自动回合有限退避，最多 3 次尝试。启动结果不明时，服务用该次请求 ID 对账原生历史。无证据时任务面板显示「Router 回执待核对」。已完成的回执会显示在 Router 对话中，浏览器重新打开后也能读取。定时任务和外部消息渠道属于后续阶段。

## 在个人微信使用当前中枢

启用 Router 后，进入「设置 → 微信接入」，选择「扫码绑定」，用本人微信扫码并在手机确认。如果微信显示 PIN，在当前工作台填写验证码。第一次绑定后，从微信发一句话，设置页会显示最近收发时间和「可接收主动通知」。浏览器可关闭，本机 Web 服务、Router 与 Worker 需持续运行。

| 交互 | 微信收到的内容 |
|---|---|
| 微信发起的 Router 对话 | 本轮最终答复或带候选项的澄清。Web 可查看同一份历史。 |
| Web 发起的普通对话 | 对话保留在 Web。 |
| Web 或微信安排的 Worker 结束、失败、中断 | 默认主动通知。回执合批仅包含本次允许外发的任务；Router 汇报延迟时，先通知已确认的执行状态。 |
| Worker 需要审批、输入或决定 | 默认主动通知。微信可查看原始命令及工作目录、文件授权范围或权限详情，选择单次允许或拒绝。 |

绑定时即打开「任务结果」「审批及决策」，两者可分别关闭。微信普通回复始终跟随原消息。共享队列串行启动 Router 回合，Web 显示排队状态；Worker 审批可在主线程运行时处理。已送达的任务回执会关联派发记录，便于继续追问。

微信将待处理的审批、Router 候选和 Worker 问题按登记顺序排队，一次只展示一项。候选支持数字、中文序数和唯一名称片段。找不到合适会话可回复「都不是」。需要语义理解时，中枢可以建议候选编号，由用户核对。权限授权需明确确认。多项审批同时开放时，可直接回复当前已送达卡片上列出的选项数字。笼统回复「允许」时会列出项目供选择。也可主动发「待办」，再回复「aaa」或「查看 aaa」调出该项目的审批详情。同名项目可用对应短码。处理完成后自动显示下一项。多题表单依次收集后一次交给原 Worker。

微信默认在当前消息确实开始处理满 3 秒后，使用 iLink 的输入状态反馈。处理期间每 5 秒刷新一次，当前回合结束或进入待办、派工时取消。无法使用输入状态时，仍在处理的请求可收到一次文字提示。排队与开始执行分别核对真实任务状态，默认满 15 秒才提示阶段变化；直接派工回执可以立即说明当前状态。等待用户沿用原审批或问题卡，终态沿用原任务回执。Web 发起的普通问答不会触发微信输入状态。[腾讯微信 iLink 协议](https://github.com/Tencent/openclaw-weixin/blob/main/docs/protocol_zh_CN.md)

在“设置 → 中枢”可以调整助手名称、自称、人格、语言风格、回复详略和微信表达偏好，以及输入状态开关和两个延迟时间。保存后从下一轮起生效。微信设置不会更改个人微信客户端里的联系人备注。

回复「下一个」或「暂不处理」会暂缓整项请求，继续展示其余待办。暂缓期间原 Worker 仍等待，原有超时继续生效。回复「待办」可重看当前题，其他待办都处理完后可用它取回暂缓项。若当前题已在 Web 处理或失效，回复「继续」后再看下一项。发「任务：…」可随时另起任务；文字题需要提交与队列指令相同的字词时可发「回答：下一个」。私密题会提示微信聊天留痕，工作台历史仅记录处理状态。审批详情按原生请求和对应操作补全。长详情分段发送，完整送达后开放允许。缺少必要操作或授权范围时可拒绝或稍后重看。

### 断线与恢复

断开连接可暂停收发并保留绑定，恢复后使用原游标。解绑清理渠道凭据及该绑定的入箱、发件箱和交互引用；主 Router 的历史仍可在 Web 查看。凭据、回复上下文和暂存答案在 Router 私有目录加密保存，恢复原绑定需要保留该目录中的 `router.sqlite` 和 `wechat.key`。

设置页显示待发送、失败、待核对计数。网络传输结果不明时保留待核对记录；服务端可能已经收到，工作台不会自动重发。已确认失效的待办会在发送或响应时失效。首次绑定只登记此后观察到的 Worker 终态，旧回执不做批量回放。协议支持范围及真人扫码验收见 [验收记录](ACCEPTANCE.md)。

### 真实微信专项验收

可使用已有测试工作台运行 `npm run test:wechat:live`。需显式设置 `WECHAT_LIVE=1`、`WECHAT_TEST_ORIGIN`（工作台 HTTPS 地址或 HTTP 回环地址）、`WECHAT_TEST_PROJECT`（测试项目 ID）和 `WECHAT_TEST_ACCOUNT`（供操作人核对的测试账号备注）。令牌认证实例另通过环境提供 `WECHAT_TEST_ACCESS_TOKEN`。脚本从已认证的 RPC 读取状态，不打印凭据或回答正文。请在自己的交互终端运行，以便最后确认手机实际收件。

使用测试账号本人扫码；关闭 Web 后从手机发起任务，在已有候选中回复「第二个」，完成命令审批和原生答题、接收结果并追问，再回 Web 核对记录。WECHAT_TEST_PROJECT 可指定项目 ID 或名称，多个目标用逗号分隔。观察脚本比对本次标记、项目、任务、响应方法和共享历史，手机实际收到结果及追问答复需操作人确认。首条消息前后、长时间空闲后的上下文有效性、频控和长文本上限单独记录实测条件及结果。

## 项目与会话记忆

启用中枢后，PSM 默认开启。在「设置 → 中枢 → 项目与会话记忆」可手动关闭 PSM，重启后保留关闭或暂停的选择。初次启用后，Worker Hub 通过只读协议分页发现本机可访问的持久顶层 Worker 历史，分别枚举使用中和归档的会话。后台线程提取用户和 Agent 文本，建立 SQLite FTS5 消息索引。未授权项目只公开项目元数据；用户确认项目访问后才返回历史命中。PSM 的阅读授权与 Worker 调度授权分别保存。设置页提供进度、失败数、最近成功时间、暂停、恢复和重试。暂停可保留已经提交的会话，正在读取的会话恢复后重新核对。

Router 可换词使用 `psm_search` 检索，再以 `psm_get` 读取消息引用并核验内容指纹。搜索会返回用户确认、派发经历、语义条目和消息证据。FTS 排名只用于候选召回。已登记项目和 Worker 的实时身份、执行配置、审批及队列仍由原有派发路径校验。归档的消息可以检索；暂时缺失和确认删除的目标不能作为续接候选。

`psm_save`、`psm_update` 和 `psm_remove` 仅管理项目用途、别名、主题、决策、约束和进展。模型推断与用户确认分别标注。用户可在 Web 或微信确认卡核实关联，也可在设置中纠正或撤销语义条目。回执工具仍只允许读取该批次的 Worker 任务。

| 操作 | 效果 |
|---|---|
| 增量同步 | 核对项目、会话和历史变动，重试失败项。服务启动、Worker 重连、原生事件及 20 分钟轮询也会触发同步。 |
| 重建 L1 | 重建私有状态目录的 `router/psm-index.sqlite`。用户确认、修订和派发事实从 `router/router.sqlite` 保留并重新投影。 |
| 撤销记忆 | 停用选定语义条目，保存修订历史。 |
| 彻底清除项目 PSM 数据 | 清理该身份的派生索引、语义条目和修订，阻止后台自动重新收录。原始项目、Codex 会话及原有业务派发记录仍由各自服务管理。 |
| 归档或删除原始会话 | 通过既有 Worker 操作执行。删除成功时清理派生正文，历史关联显示失效。 |

专用 Router 策略 v2 精确允许 12 个工具；v1 继续提供原有 7 个工具。更新专用构建后，启用 PSM 的既有主会话在服务端确认空闲后自动切换。两个渠道共用同一主指针，沿用授权、模型选择、微信绑定和记忆。旧原生历史可在中枢对话的「旧中枢会话记录」分页查看。若创建响应丢失且新 ID 不可证实，系统保留当前主会话并显示待核对状态。

只读真实历史验证可运行 `scripts/test-psm-live.mjs`。显式设置 `CODEX_WEB_PSM_LIVE=1`、`CODEX_WEB_LIVE_HOME`、`PSM_CWD`、`PSM_THREAD` 和 `PSM_QUERY`。脚本只为指定会话建立临时索引，核对命中消息并输出数量、校验结果与耗时。

## RCC 模式与任务

Web 中枢页显示当前模式。微信可发送「当前模式」「切换任务模式」「切换聊天模式」或「任务列表」。任务模式下直接提问即可。例如先问「aaa 的测试覆盖哪些情况？」，再问「bbb 的测试为什么失败？」「怎么修？」，后两条都会交给 bbb 的对应会话。若有多个可能的会话，Router 会请你说明指的是哪一项。

Web 和微信分别承接各自对话中的任务。查询状态或收到自动回执后，仍可继续刚才的业务问题。有未答待办时，可用「任务：…」单独补充业务，或用「回答：…」回答已展示的问题。审批仍须按对应卡片选择。

「刚才发错了，停下」「取消指令 #编号」和任务卡的「纠正误派」会展示目标供确认。未提交的指令可直接取消，仍在原生队列的指令按队列身份撤回，进行中的回合按原 Thread 和 Turn 请求中断。任务面板展示原生中断结果或已结束回合的实际结果。若错误指令已进会话，其纠正说明随该会话下一次正常续接发送。停止结果超时可在原 Worker 核对后用任务卡关闭。

## 升级官方 Worker 后的协议检查

`zcodex doctor --json` 在实例运行时返回 `worker.version`、`worker.kind` 和 `worker.protocol`。顶层的 `codexVersion` 来自当前安装路径，连接共享 daemon 时可能与它实际运行的版本不同。queue、steer 分别表示已验收的队列和插话能力。仅 queue 通过时，忙碌回合的补充继续在 RCC 等待空闲。

Linux arm64 的官方 0.172.0 已包含两种传输的实测记录。对于新的 Linux 构建，选用实际运行的官方 Codex 可执行文件，在有 user/network/PID namespace、`unshare` 和 `ip` 的机器上运行以下命令。daemon 选项创建临时 Unix socket 服务器。stdio 选项创建私有 stdio 服务器。两者均使用临时 HOME、临时项目和本地模型夹具。

```sh
zcodex verify-worker --codex "$(command -v codex)" --transport daemon > worker-protocol.new.json &&
  mv worker-protocol.new.json worker-protocol.json
```

把应用 JSON 顶层的 `workerProtocolReport` 设为这个文件的绝对路径，保存到仅由工作台管理员维护的位置。选择与部署相同的传输。在维护窗口让工作台重连，使用 doctor 核对实际运行版本、传输以及 `source: "fixture"`。若完整检查失败而只需要队列，可追加 `--queue-only` 单独验收队列。旧报告和实际二进制、平台或传输不匹配时，工作台会关闭该报告控制的派发能力。失败且确认尚未送达的指令可以重新提交，unknown 指令仍须先在原 Worker 核对。

工作台版本更新使用原有 `zcodex update` 流程。启用 Router 时继续使用经摘要核对的专用启动器。详细证据和跨平台限制见仓库中的 UAS 实施计划。
