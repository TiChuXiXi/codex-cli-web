# 差异与文档冲突

## 允许的独立外壳差异

- 新增 Node CLI、HTTP、静态资源、配置、认证、登录和登出。
- 服务代码整理为 server，前端整理为 web，共用契约和限制放 shared；完整映射见 migration-map.json。
- React 由应用显式提供；不再使用 DSH slots/layout/locale/connection/ModuleLoader。
- 原宿主返回入口改为同位置“退出 Web 登录”；视觉对比只屏蔽该控件。
- runtime 从新工程文件生成 buildId/instanceId；前端请求地址统一通过 URL helper。

## 设置面板下拉框

Worker、中枢及项目与会话记忆设置复用工作台的 SelectMenu，保留原有选项、联动和保存逻辑。中枢表达设置使用多行文本域，复选框、PSM 和微信操作组适配设置页布局。

## 新项目修复

- 严格 TypeScript 检查修正了 Ref 初值、词典索引、turn.durationMs、BlobPart、品牌 ID 和 cloneElement props 类型。
- Hub 在初始化失败或关闭期间释放已打开传输，重连等待支持取消，初始化期间 stop 不再遗漏私有子进程。
- 版本服务增加子进程、fetch 和计时器清理，并为探测与作业传递显式 CODEX_HOME。版本作业使用 close 事件结束失败状态，修复 spawn 失败永久 running；Linux 子进程组在退出时终止，包含挂起的诊断进程。新增 test/versions.test.mjs 覆盖。
- SSE hello 增加应用 instanceId；实例变化或序号回退触发 resync，重新拉取当前详情与队列。新增 epoch 单元测试。
- 浏览器相关 ID 兼容显式配置的 HTTP 局域网 origin，使用 getRandomValues 兜底。
- 修复多题表单进入末题时提前提交的问题。点击「下一题」只切换题目，末题的「提交」统一发送答案。浏览器回归覆盖后续题已有默认选项、键盘翻页及返回修改。

## 子代理执行明细

主会话按子线程 ID 合并子代理活动，原位展开查看消息、命令、工具与文件变更。支持 Codex 的 `subAgentActivity` 与 `collabAgentToolCall`，复用已认证的 SSE，运行中的展开卡片通过只读历史补查恢复缺口。新增认证 RPC `threads/subagent/get`，核对直属关系后读取分页历史，临时子线程按 Codex 接口可用性降级。委派任务文本取自协议公开字段或子线程用户消息，缺失时隐藏该部分。

构建与类型检查通过。模拟浏览器覆盖两个代理并行更新、断线补查、历史分页、刷新恢复和桌面、窄屏显示。用独立 Codex CLI 0.170.0 进程和「事件机制调研」的定向历史副本验证了 Kepler、Lorentz 可分别展开并读取已完成的活动；原会话和共享 daemon 未参与此验证。运行期间的行为由夹具覆盖。

候选和审批共用既有 Router 澄清、Worker 原生请求和微信队列。手机显示待办短码，多审批先明确目标。会话选择优先匹配编号、中文序数和唯一名称，语义建议需要用户核对。详情不足时暂缓批准，内容较长时分段送达。Web 和微信的审批详情使用同一字段投影。回执读取同一派工的微信待办历史和 Worker 结构化问题的已答状态，核对 Web 或微信提交的答复。单任务完成答题且 Worker 结果简短时，微信发送 Worker 原文。

明确分别续接多个具名项目时，Router 用每条消息与项目的组合区分操作，各项目沿用既有授权和 Worker 队列。Web 与微信按照原生请求显示“取消”或“拒绝”，保留两种决定的协议语义。已提交的原生审批与公开选项由现有解决事件关联至对应派工。

按操作人更新的实施顺序，P1 和 P2 已在同一工作台加载，并与 P0 合并进行微信真机验收。微信复用当前 outbox，根据 Router 回合和 Worker 事件反馈进度。输入状态沿用 iLink 绑定与既有投递循环，慢回复期间每 5 秒刷新一次，派工或结束后取消。显示名称和风格在每轮动态上下文中生效，沿用原主会话、工具策略和项目授权。

微信双审批以入站时已送达卡片的实例、题号和展示版本定位数字选项。笼统的允许仍需消歧。待办菜单内直接回复项目名只调出详情，待用户另行决定。

## RCC P0 的 Worker 指令交付

Router SQLite v4 使用同一派发 ID 关联原文、Worker 和独立的交付证据。Dispatcher 按 Thread 分别推进，复用工作台 FollowupQueue 的提交锁。0.170.0 的普通续接可通过 Steer 进入活动回合。明确要求下一回合、未验收的等待类型及旧版本按原生空闲队列续接。任务面板显示阻塞指令编号、核对记录和人工关闭入口。

协议回包、历史可见性和所属回合终态分别记录。连续补充共享原回合的终态回执。Web 与微信仍沿用已有 Router 入口和待办系统。共享模式、各渠道焦点和自然语言快速转交属于 P1。复现步骤和实测数据见 [RCC P0 验收记录](acceptance/rcc-p0.md)。

## RCC P1 / P2

- 微信普通派发由当前原生 Router 回合绑定入站请求编号。待定位的原问题在同一对话补充项目或会话名后继续用于派发与权限确认。

- Worker 普通派发只发送用户原文，适用于新建会话、续接和运行中追加。误派纠正仍单独传递纠正说明。

RouterStore 保存共享模式版本、按渠道区分的焦点版本、每次受理的目标快照和误派处置记录。任务模式的明确续接复用 Dispatcher，原生中断、原生队列撤回和完成通知复用 Worker Hub、现有队列和事件。微信待办焦点和业务焦点分别处理。验收证据及真机进度见 [RCC 统一验收记录](acceptance/rcc-unified.md)。

操作者确认后，Web 移除了手动设置和展示业务焦点的控件，微信任务列表仅列任务与进度。服务端按提问内容选择项目和会话；同批到达的追问关联到本渠道上一条业务消息的选择结果。

## RIP 身份与表达

中枢设置中的“助手与表达”使用配置与预览双栏，窄屏上下排列。三种人格预设仅载入亲和程度、活泼程度、表达结构的初始档位，六项表达策略独立保存。普通回复和自动回执在既有线程逐轮读取设置，系统通知按实际状态渲染。原有自由文本保留来源，微信偏好保留渠道范围。[配置效果、页面截图及回归记录](acceptance/router-rip.md)
