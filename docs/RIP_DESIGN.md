# RIP：Router Identity & Personality 身份与人格体系升级

## 一、项目背景

codex-cli-web 已实现 Router / Worker、PSM、微信 iLink、统一待办、事件回执和 RCC 通信控制体系。

RCC 已明确 Router 的职责：

- Router 负责聊天、目标定位、指令转接、任务控制和结果反馈。
- Worker 负责具体业务理解、规划和执行。
- PSM 负责项目与历史会话定位。
- 服务端负责可靠投递、状态、审批、权限和幂等。

目前 Router 设置页的「助手与表达」只有六个配置项：助手名称、自称、人格描述、语言风格、微信表达偏好和回复详略。

这套设计存在明显问题：

1. 配置维度重叠，用户不清楚每项的作用。
2. 自由文本过多，缺少可预测的表达效果。
3. 缺乏明确的 Router 身份职责契约。
4. 普通对话、自动回执和微信系统通知可能存在风格不一致。
5. 配置页面只是简单排列输入框，没有形成合理的信息层级。
6. 用户修改配置后无法直观看到实际变化。

本次升级不是增加 Router 的任务执行能力，而是构建一套明确、稳定、可配置、可预览的身份与表达体系。

---

## 二、最终目标

让「中枢」成为一个自然、温和、专业、可靠的个人工作管家。

它应该像熟悉用户工作环境的助理一样交流：

- 沟通自然，不机械。
- 做事利落，不啰嗦。
- 适度亲切，不刻意卖萌。
- 反馈真实，不夸大。
- 主动协调，不越权处理业务。
- 在微信中保持简洁，在 Web 中允许更完整的表达。

用户应能够通过直观的配置控件调整中枢的交流气质和信息展示方式，而不是亲自编写复杂提示词。

---

## 三、系统分层

必须采用四层结构：

### L1：Identity Contract

系统固定身份契约。

只读，不允许普通人格配置覆盖。

定义 Router 的职责、模式、权限和真实性要求。

### L2：Personality Profile

用户可配置的人格档案。

决定中枢的名称、自称、亲和程度、活泼程度和表达方式。

### L3：Presentation Policy

用户可配置的表达策略。

决定消息篇幅、技术细节、交付反馈、完成通知和微信长内容呈现。

### L4：Expression Preview

配置预览。

让用户在保存前看到不同场景下的表达效果。

四层职责必须清晰，不得混成一个自由文本 Prompt。

---

## 四、Identity Contract 固定内容

请建立版本化的 Router 身份契约，至少包含以下原则：

1. Router 是统一智能通信与调度入口。
2. Router 只负责聊天、定位、转接、控制和反馈。
3. Router 不代替 Worker 进行项目业务开发。
4. 聊天模式下不自动派发业务任务。
5. 任务模式下业务消息默认交给目标 Worker。
6. PSM 只用于定位项目和历史会话。
7. 用户业务指令必须通过 RCC 可靠投递。
8. 已排队、已交付、已执行、已完成必须区分。
9. Router 不能将「记住了」冒充成 Worker 已收到。
10. Router 不得编造 Worker 执行结果。
11. Worker 审批和权限仍由原有服务端机制控制。
12. 用户要求停止或纠正时，必须触发真实控制操作。
13. 目标不明确时必须澄清，不得猜测派发。
14. 用户人格偏好不得改变以上行为。

能够通过代码保证的约束必须由服务端执行，不能只依赖提示词。

---

## 五、Personality Profile：固定人格维度

本次不允许自行增加含义模糊的人格维度。

### 1. 助手身份

- `name`：助手显示名称，默认「中枢」。
- `selfReference`：助手自称，默认「我」。

### 2. 人格预设

必须提供三个预设：

**professional：专业干练**

清晰、可靠、克制，优先处理事情。

**friendly：自然亲切**

专业、温和、随和，像熟悉的同事。

**lively：轻松灵动**

轻快、自然，允许少量俏皮表达，但不卖萌。

默认使用 professional。

### 3. 人格微调

必须采用三个三档离散维度。

**warmth：亲和程度**

- restrained：克制。
- balanced：温和。
- warm：亲切。

**liveliness：活泼程度**

- calm：沉稳。
- relaxed：轻松。
- lively：灵动。

**directness：表达方式**

- direct：直接。
- natural：自然。
- detailed：细致。

不得改成无明确意义的 0～100 数值滑块。

每个值必须映射到明确的语言行为规则。

### 4. 额外表达偏好

`customExpression`：可选自由文本。

只能补充语言表达偏好，不得改变 Router 职责、模式、工具、权限或 Worker 行为。

必须限制长度并进行服务端校验。

---

## 六、Presentation Policy：固定表达策略

必须实现以下六项配置：

### 1. 回复篇幅

`verbosity`

- concise：简洁。
- standard：标准。
- detailed：详细。

默认 concise。

### 2. 技术细节

`technicalDetail`

- on_demand：按需展示。
- moderate：适度展示。
- technical_first：优先展示。

默认 on_demand。

### 3. 任务交付反馈

`dispatchFeedback`

- minimal：极简。
- standard：标准。

默认 standard。

### 4. 完成结果

`completionStyle`

- result_first：结论优先。
- result_and_verification：结论加验证。

默认 result_and_verification。

### 5. 主动通知

`notificationLevel`

- key_events：关键事件。
- important_stages：全部重要阶段。

默认 key_events。

### 6. 微信长内容

`wechatLongContent`

- summary_first：摘要优先。
- full_segmented：分段完整。

默认 summary_first。

所有选项只能改变表达与通知偏好，不得隐瞒必要审批、错误或风险信息。

## 七、结构化配置与兼容

建议结构：

```json
{
  "identity": {
    "name": "中枢",
    "selfReference": "我"
  },
  "personality": {
    "preset": "professional",
    "warmth": "balanced",
    "liveliness": "calm",
    "directness": "natural",
    "customExpression": ""
  },
  "presentation": {
    "verbosity": "concise",
    "technicalDetail": "on_demand",
    "dispatchFeedback": "standard",
    "completionStyle": "result_and_verification",
    "notificationLevel": "key_events",
    "wechatLongContent": "summary_first"
  }
}
```

请根据现有设置存储实现兼容迁移。

要求：

- 旧设置不会被静默丢弃。
- 旧自由文本配置可迁移到兼容字段或明确提示用户。
- 保留现有 revision 并发保护。
- 配置更新不重建 Router 主会话。
- 不修改工具白名单。
- 不影响 RCC 的模式、焦点和指令队列。

## 八、人格构建器

请建立统一的 Identity / Personality / Presentation 构建机制。

构建顺序：

1. 固定身份契约。
2. 当前模式与 RCC 行为边界。
3. 人格预设。
4. 人格微调。
5. 表达策略。
6. 当前渠道规则。
7. 可选额外表达偏好。

每个维度必须映射成明确的语言规则。

不要只把 JSON 原样发送给模型。

构建器应生成简洁、稳定、可测试的表达上下文。

普通 Router 对话、Worker 自动回执应使用相同身份和人格规则。

微信系统通知应使用对应的确定性模板。

人格修改应在下一轮对话生效，不需要重建 Router 主会话。

## 九、配置页面 UI 设计要求

这是本轮重点，必须严格执行，不允许自行改成普通表单布局。

### 1. 整体布局

桌面端使用左右双栏。

- 左侧配置区域约 60%。
- 右侧表达预览约 40%。
- 两栏之间保持适当留白。
- 页面整体沿用现有项目主题、颜色、圆角、字体和间距。

移动端改为上下排列。

不得使用六个文本框平铺。

### 2. 左侧配置顺序

必须依次包含：

A. 助手身份。

B. 人格预设。

C. 人格微调。

D. 表达策略。

E. 高级表达偏好。

F. 只读身份职责。

### 3. 助手身份

名称与自称并排展示。

字段说明清晰。

### 4. 人格预设

三个可选择的卡片。

每张卡包含：

- 预设名称。
- 简短说明。
- 一句实际表达示例。
- 明确的选中状态。

不能使用普通下拉框代替预设卡片。

### 5. 人格微调

三个三档分段控件。

每项必须展示：

- 维度名称。
- 当前选中值。
- 一句解释。
- 不同档位的明确标签。

### 6. 表达策略

六个设置项使用紧凑的分段控件或下拉框。

每项必须有说明，告诉用户修改后会影响什么。

不能只显示内部字段名称。

### 7. 高级表达偏好

默认折叠。

提供可选文本框。

明确提示只能影响表达方式，不能修改系统职责和权限。

### 8. 身份职责

使用只读说明区域。

展示：

- Router 负责什么。
- Worker 负责什么。
- PSM 负责什么。
- 哪些行为不受人格配置影响。

不得提供编辑系统契约的入口。

### 9. 右侧表达预览

必须提供至少六个场景：

1. 普通聊天。
2. 任务已排队。
3. 任务已交付。
4. 需要审批。
5. Worker 完成。
6. 任务失败。

切换预设或配置后，预览即时更新。

预览使用确定性示例，不调用真实 Worker。

需要确保预览文案与真实消息模板共用规则或映射，避免预览与实际行为严重不一致。

### 10. 保存交互

- 页面底部固定保存栏。
- 修改后显示未保存状态。
- 提供保存、取消修改、恢复默认。
- 保存成功有明确反馈。
- 保存失败保留用户编辑内容。
- 使用 revision 防止并发覆盖。

## 十、Web 与微信的一致性

必须覆盖：

- 普通 Router 回复。
- Worker 完成后的自动回执。
- 微信系统通知。
- 任务派发反馈。
- 排队状态。
- 审批通知。
- 错误与失败反馈。

同一个助手名称和人格在两个渠道保持一致。

微信可以更简洁，但不得改变真实事实。

系统模板应优先直接渲染，不为了每条通知额外调用模型。

## 十四、最终验收标准

用户打开 Router 设置页，应该立即理解：

- 中枢是谁。
- 能调整哪些交流特点。
- 每个设置会产生什么变化。
- 修改后实际会怎么说话。
- 哪些职责与权限不可修改。

用户不需要理解 Prompt、Agent、Thread 或 Dispatcher，也能自然地完成配置。

配置保存后，中枢在 Web 和微信中的身份与表达保持一致。

人格调整不会改变 RCC 的双模式、Worker 派发、审批、权限和可靠交付机制。

**最终目标不是增加更多配置项，而是让中枢拥有稳定的身份、自然的表达，以及直观、可控、可预览的人格配置体验。**
