# codex-cli-web：Project & Session Memory（PSM）项目与会话记忆系统

## 一、项目背景

### 1. 现有系统

codex-cli-web 是基于 Codex App Server 的独立 Web 工作台，已经具备：

- 多项目、多会话管理。
- Codex 原生 Worker 执行与会话续接。
- Router 统一智能交互入口。
- Router 智能匹配项目与会话、派发任务。
- Worker 执行状态、审批、用户决策及结果反馈。
- 微信 iLink 远程交互渠道。
- Router 与 Worker 的任务关联和事件驱动机制。

目前 Router 已经基本可用。用户可以通过 Web 或微信描述需求，由 Router 选择项目、续接 Worker 并处理执行反馈。

### 2. 为什么需要 PSM？

虽然 Router 已经能够智能匹配项目和会话，但目前它对整个工作环境的认识仍然不足。

Codex 的项目通常只是一个工作目录，项目名称未必能反映真实业务。

Codex 会话的标题也可能非常笼统，而且一个会话中可能包含多个不同任务。

例如：

- 项目目录：`aaa`
- 会话标题：`优化方案`
- 会话实际内容：USB HUB 掉线、xHCI 异常、设备枚举失败、供电恢复等问题。

当用户说：

「去看看之前 USB 掉线的问题修得怎么样了。」

即使 Router 使用很强的模型，也无法仅凭 `aaa` 和「优化方案」两个名称可靠地找到正确会话。

如果每次都需要重新读取大量历史聊天记录，效率低、消耗上下文，而且容易遗漏。

如果用户已经告诉过 Router 这个问题属于哪个项目、哪个会话，却仍然需要反复解释，就失去了智能助手的意义。

**因此，需要建立一套持续维护的项目与会话认知索引，让 Router 能够理解整个 Codex 工作环境，并随着实际使用不断积累准确的工作经验。**

---

## 二、PSM 的定义与边界

PSM 全称：

**Project & Session Memory — 项目与会话记忆。**

PSM 特指 codex-cli-web 中项目、Worker 会话及其工作历史的认知记忆系统。

它不是通用 AI Memory。

不负责记录用户的生活信息、个人习惯、情感关系或其他与项目和会话无关的长期信息。

PSM 只管理：

- 项目身份、名称、路径、用途和业务含义。
- Worker 会话身份、标题、内容及历史变化。
- 会话中的问题、讨论、决策、任务和执行结果。
- Router 对项目、会话的实际使用经历。
- 用户对项目、任务、会话的自然语言称呼。
- 用户明确确认、补充和纠正的关联信息。
- 项目与会话的生命周期状态。

PSM 的数据应独立于 Router 当前使用的模型、Codex Thread 和微信渠道。

即使 Router 重建会话、更换模型或重启服务，PSM 仍然可以继续使用。

---

## 三、最终目标

**让 Router 不再依赖项目名称和会话标题进行浅层匹配，而是能够根据用户自然语言，从整个项目和会话生命周期中快速找到相关工作。**

最终希望达到以下体验。

### 场景一：首次查找陌生任务

用户：

「看看之前 USB 掉线的问题。」

Router 首先检索 PSM。

如果已有原生聊天记录包含相关内容，应能够找到对应的项目、会话及相关消息。

如果存在多个相似候选，应提供必要信息让用户确认，而不是猜测。

### 场景二：用户补充项目信息

用户：

「aaa 就是之前那个嵌入式设备控制项目。」

Router 应当识别这是值得保存的项目语义信息，通过 PSM 工具更新项目档案。

以后用户说「设备控制项目」，Router 能够关联到 `aaa`。

### 场景三：用户确认任务位置

用户：

「USB 掉线就是 aaa 项目里那个优化方案会话。」

Router 应保存经过用户确认的任务与会话关联。

以后再次提到 USB 掉线，应优先使用该关联，并核实目标是否仍然有效。

### 场景四：Router 执行任务后积累经验

Router 将某个需求派发到 Worker。

Worker 完成后，系统记录：

- 用户当时如何描述任务。
- Router 最终选择了哪个项目和会话。
- 实际执行了什么。
- Worker 的执行结果。
- 后续是否继续处理。

下次用户说「继续刚才那个问题」，Router 应能够利用此前的工作经历快速定位。

### 场景五：项目和会话持续变化

项目新增、会话续接、新 Turn 完成、标题修改或外部 Codex CLI 产生新的会话时，PSM 应自动更新索引。

不要求用户手动重新建立索引。

### 场景六：项目或会话删除

当原始项目或会话被删除、归档或暂时无法访问时，PSM 应正确更新来源状态。

历史工作经历不应被无条件清空，但失效来源不能再被当作有效 Worker 目标。

## 四、总体架构：两层索引 + 用户纠正

### L1：原生项目与会话索引

**Source Index**

数据来源：

- Codex 项目。
- Worker Thread。
- Turn。
- 用户消息。
- Agent 回复。
- 可访问的历史会话记录。

由 Node.js 程序机械化维护。

主要职责：

1. 首次扫描全部可访问项目与会话。
2. 建立项目、会话、Turn、消息之间的关系。
3. 保存必要的原始文本与来源引用。
4. 建立 SQLite FTS5 全文检索。
5. 跟踪项目和会话的增量变化。
6. 处理归档、缺失、删除和路径变更。
7. 提供从索引返回原始消息的能力。

一个会话可能包含多个主题，因此必须支持消息级或内容片段级检索，不能只保存一个会话摘要。

L1 是可重建的派生索引，不允许 Router 修改原始 Codex 历史记录。

### L2：Router 工作经历与语义记忆

**Router Experience Index**

数据来源：

- Router 历史对话。
- Router 派发记录。
- Worker 执行结果。
- Router 实际选择的项目和会话。
- Router 在交流中理解到的项目语义与任务关联。

采用两种写入方式。

**A. 程序自动记录确定性事实**

例如：

- Router 派发到哪个 Thread。
- Worker Turn 是否完成。
- 派发时间。
- 实际任务目标。
- 执行结果。
- 用户明确选择的候选。

这些信息已经存在于系统中，不需要模型再次推断。

**B. Router 智能维护语义记忆**

例如：

- 项目 `aaa` 是嵌入式设备控制项目。
- 用户说的「USB 掉线」与某个历史会话有关。
- 「设备失联」「USB HUB 掉线」可能是同一主题的不同表达。
- 某个任务此前已经采用了什么方案。
- 某项技术决策存在什么重要约束。

Router 在正常对话中发现值得记住的信息时，可以主动调用 PSM 工具新增、更新或撤销语义记忆。

不需要每轮对话强制写记忆。

### L3：用户确认与纠正机制

L3 是对 L1、L2 的纠错和补充机制，不是独立的通用记忆库。

当 Router 无法可靠匹配目标时，应向用户提供候选。

用户确认后，系统记录确认结果。

当用户纠正错误关联时，应更新有效关联，并保留必要的纠正历史。

用户明确确认的事实，优先级应高于未经验证的模型推断。

但用户确认的历史关联也必须经过来源有效性检查，不能因为曾经正确就永久假设仍然正确。

## 五、借鉴 AOCI-CODE 的设计思想

参考项目：

https://github.com/aoci-spec/aoci-code

AOCI-CODE 是面向 AI Agent 的软件认知索引项目。

它强调：

- 将高价值信息组织成可持续维护的认知索引。
- 让 Agent 优先阅读索引，而不是每次重新理解完整系统。
- 保留对象关系和关键约束。
- 通过 Baseline、变更检测、校验和增量维护保证索引与来源一致。
- 让模型负责语义判断，让程序负责确定性的索引治理。

本项目借鉴这些设计思想，但不直接照搬其代码索引格式、Go CLI、MCP 运行时或完整事务治理协议。

PSM 的数据对象是项目、会话、消息和工作经历，而不是代码符号。

**特别要求：不要因为参考 AOCI-CODE，就额外引入一个独立索引 Agent。**

第一版采用：

- Node.js 确定性索引引擎。
- SQLite + FTS5。
- 现有 Router Agent 的智能判断能力。
- Router 专用 PSM 读写工具。

不引入向量数据库、独立索引 Agent 或复杂知识图谱。

若未来需要复制 AOCI-CODE 的具体源码，应先核实其 FSL-1.1-MIT 许可证及相关条款。

## 六、L1 首次建立与持续同步

### 1. 首次建立

首次启用 PSM 时，扫描当前 Codex App Server 能够访问的项目、Worker 会话和历史消息。

建议建立：

- 项目索引。
- 会话索引。
- Turn 索引。
- 消息全文索引。
- 项目与会话关联。
- 同步状态及来源引用。

不扫描所有项目源码文件，也不要求模型阅读每个代码仓库。

对于项目业务语义，优先使用已有项目描述、用户确认信息和会话原文。

不得根据目录名称凭空生成业务含义。

### 2. 事件驱动增量更新

优先复用 codex-cli-web 现有 Hub 和 EventBus。

需要处理：

- 新建项目。
- 新建会话。
- 新 Turn 完成。
- 会话标题变化。
- 会话归档。
- 项目路径变化。
- 项目或会话删除。

Worker Turn 完成后，异步触发对应会话的索引更新。

索引更新不得阻塞 Worker 执行、Router 对话或微信消息接收。

不需要对每个流式 Token 更新索引。

### 3. 外部变化对账

必须考虑用户直接使用 Codex CLI 或 Codex 桌面端产生的会话变化。

这些变化未必经过 codex-cli-web 的业务接口。

因此，除了事件监听，还需要轻量对账机制：

- 服务启动时对账。
- App Server 重新连接后对账。
- 定期检查项目和会话元数据。
- 支持手动触发增量同步。

建议初始定期对账间隔为 15～30 分钟，最终根据实际数据量和性能测试调整。

### 4. 增量同步水位

每个会话维护同步进度。

建议包含：

```json
{
  "threadId": "thread-123",
  "lastIndexedTurnId": "turn-456",
  "lastIndexedAt": "2026-11-19T06:00:00Z",
  "syncStatus": "synced"
}
```

这只是逻辑示例，实际字段以 Codex App Server 提供的稳定标识为准。

同步要求：

- 只处理新增或变化的数据。
- 使用稳定 ID 实现幂等更新。
- 数据成功提交后才能推进同步水位。
- 同步失败可以安全重试。
- 对可能修改的历史记录进行内容校验。
- 不能仅凭最后一个 Turn ID 假设历史内容永远不变。

### 5. 同步失败与恢复

需要支持：

- 单个会话同步失败后重试。
- 服务重启后继续未完成同步。
- App Server 断线恢复。
- 索引损坏后的重建。
- 手动强制重新扫描。

索引失败不能导致 Router 或 Worker 无法正常使用。

PSM 应作为辅助认知系统，而不是整个 Codex 工作台的单点故障。

## 七、L2 工作经历的自动记录

Router 派发任务时，程序应自动记录：

- Router Thread ID。
- 用户原始需求。
- 目标 Project ID。
- 目标 Worker Thread ID。
- Dispatch ID。
- 派发时间。
- 任务状态。
- Worker Turn ID（可获取时）。
- 执行结果。
- 最近更新时间。

这些属于确定性工作事实。

不要要求 Router 模型重新总结这些 ID 或判断它实际调用了哪个 Worker。

Router 可以在此基础上补充：

- 任务的自然语言主题。
- 用户习惯的任务称呼。
- 与其他历史任务的关联。
- 重要技术决策。
- 业务约束。
- 已确认的项目语义。

必须区分「Codex Turn 已结束」和「业务问题已解决」。

不能因为 Turn 正常完成，就自动把任务标记为已经彻底解决。

## 八、Router PSM 工具

建议为 Router 提供以下受控工具：

| 工具 | 职责 |
|---|---|
| `psm_search` | 搜索项目、会话、消息、任务和历史关联 |
| `psm_get` | 获取指定索引条目、来源及关联信息 |
| `psm_save` | 新增项目描述、别名、任务主题或关联 |
| `psm_update` | 更新已有语义记忆或任务进展 |
| `psm_remove` | 撤销、废弃错误或过期的语义记忆 |

工具命名可以根据当前 Router 的工具体系调整。

### 工具权限要求

Router 只能通过 PSM 服务访问记忆数据库。

不得开放任意 SQL 执行能力。

不得通过 PSM 工具修改原始 Codex 项目文件、聊天历史或 Worker 权限。

写入时由服务端校验：

- 目标项目是否存在。
- Thread ID 是否有效。
- 项目与会话是否匹配。
- 来源证据是否存在。
- 是否存在冲突。
- 是否允许覆盖。
- 是否需要用户确认。

模型不能自行将推测标记为 `user_confirmed`。

用户确认来源应由服务端根据真实交互记录建立。

## 九、PSM 的智能检索流程

Router 收到需要查找历史项目或会话的请求时，建议按以下顺序处理：

1. 查找已经确认的任务与会话关联。
2. 查找 Router 历史工作经历。
3. 查找项目语义描述、别名和任务主题。
4. 查找 L1 会话与消息全文索引。
5. 必要时读取相关原始聊天记录。
6. Router 综合证据判断。
7. 目标明确则直接续接。
8. 目标不明确则提供少量候选供用户确认。
9. 用户确认后持久化新的关联。

检索结果应包含：

- 项目和会话身份。
- 相关内容摘要或原文片段。
- 匹配来源。
- 来源时间。
- 来源是否仍然有效。
- 用户是否曾经确认。
- 能否直接续接。

### 语义匹配

第一版不使用向量数据库。

优先采用：

- SQLite FTS5。
- 已确认的项目和任务别名。
- 任务主题关联。
- Router 根据用户意图生成补充检索词。
- 按需读取原始会话内容。

不能将全文检索分数直接当作真实的语义置信度。

如果多个候选无法可靠区分，必须询问用户。

## 十、Router 智能记忆维护

Router 应当在自然交流中识别值得保存的项目信息。

### 应保存的情况

- 用户明确解释某个项目的用途。
- 用户确认某个任务所在的项目或会话。
- 用户纠正错误的项目或会话关联。
- 用户明确提出重要技术约束。
- Router 完成一次可靠的任务定位。
- Worker 返回具有持续价值的重要任务结果。

### 不必保存的情况

- 普通闲聊。
- 临时性、无持续价值的问题。
- 没有可靠来源的模型猜测。
- 已经由程序确定性记录的重复信息。
- 大量无意义的中间执行日志。

### 记忆来源等级

建议至少区分：

- `source_verified`：原始记录可直接验证。
- `user_confirmed`：用户明确确认。
- `router_observed`：Router 实际执行和使用经历。
- `model_inferred`：模型推断，尚未确认。

来源等级不等于绝对正确性。

未经确认的推断不能静默覆盖已确认事实。

## 十一、项目和会话生命周期管理

### 来源状态

建议至少支持：

| 状态 | 含义 |
|---|---|
| Active | 来源正常存在 |
| Archived | 来源已归档 |
| Missing | 暂时无法访问 |
| Deleted | 已确认删除 |

### 删除处理原则

**1. 一次扫描失败不能认定来源已删除。**

目录移动、磁盘未挂载、App Server 异常，都可能造成暂时不可访问。

先标记 Missing，再通过可靠证据确认。

**2. 来源删除后，不能继续派发。**

即使 L2 仍保留历史任务关联，也不能将已删除的 Worker Thread 作为有效续接目标。

**3. L1 与 L2 生命周期分离。**

L1 是原始数据的可重建索引。

L2 是 Router 工作经历。

来源删除后，L1 原文缓存按保留策略清理；L2 可以保留必要的历史工作事实，但必须标记来源失效。

**4. L3 纠正记录不能自动消失。**

用户曾经纠正过的错误关联，可以作为历史证据保留，但不能继续作为有效派发依据。

**5. 支持明确的数据清除操作。**

普通删除与彻底清除需要区分。

如果用户明确要求彻底清除某项目的 PSM 数据，应清理可控范围内的索引、语义关联、历史副本及相应全文检索记录。

不能将「软删除」作为拒绝真正清除数据的理由。

### 同名项目重建

不能仅凭相同目录名称或路径认定新项目就是旧项目。

PSM 应使用稳定内部身份。

项目移动、恢复、重建时，通过可靠证据或用户确认决定是否延续原有身份。

## 十二、存储方案

第一版优先使用 SQLite + FTS5。

建议逻辑数据结构包括：

- `psm_projects`
- `psm_threads`
- `psm_turns`
- `psm_messages`
- `psm_sync_state`
- `psm_semantic_entries`
- `psm_topic_links`
- `psm_router_experiences`
- `psm_memory_revisions`

以上是逻辑划分，不要求严格创建九张表。

应优先检查现有 Router SQLite 数据库，避免重复存储已有的派发记录和执行结果。

### 数据原则

- 原始 Codex 数据是事实来源。
- L1 索引是可重建的派生数据。
- L2 确定性工作事实尽量引用已有记录。
- Router 语义记忆独立保存。
- 所有语义记忆保留来源和修改记录。
- 使用事务保证索引与同步水位一致。
- 不将 PSM 默认写入各项目 Git 仓库。
- 不允许原始消息内容通过索引检索结果获得额外工具权限。

对于含有密钥、凭据和其他敏感信息的消息，应设置合理的索引排除或脱敏规则，并沿用现有服务访问控制。

## 十三、与现有 Router 的集成

PSM 是 Router 的辅助认知能力，不替换 Router。

不得重新开发：

- Router / Worker 调度体系。
- Codex App Server 通信。
- Worker 执行队列。
- 审批和决策回传。
- 微信 iLink 通信。
- Router 事件驱动机制。

PSM 应接入现有服务层。

Router 的主要变化应当是：

**原来：**

收到需求 → 根据项目和会话标题匹配 → 派发。

**现在：**

收到需求 → 检索 PSM → 必要时阅读原文 → 判断目标 → 派发 → 更新工作经历与语义记忆。

如果 PSM 不可用，Router 应能回退到现有项目和会话查找能力。

使用真实历史项目和会话进行测试，重点检查检索准确率、同步可靠性、记忆纠正和性能。

## 十六、必须通过的验收场景

### 测试一：无意义项目名称

项目名 `aaa`，会话名「优化方案」，原始消息讨论 USB HUB 掉线。

用户说：

「找一下 USB 掉线问题。」

Router 应能通过原生消息索引找到相关候选。

### 测试二：用户确认后复用

用户确认 USB 掉线属于 `aaa` 的「优化方案」会话。

系统保存关联。

再次提出相同或相近需求时，应优先找到该会话。

### 测试三：Router 工作经历

Router 派发一次任务，Worker 完成。

PSM 应记录这次使用经历。

用户之后说「继续上次那个任务」，Router 能利用历史关联。

### 测试四：会话新增内容

Worker 新增 Turn，讨论新的 USB 稳定性测试结果。

PSM 应自动增量更新，不必全量重建。

### 测试五：外部 Codex CLI

用户绕过 Web，直接通过 Codex CLI 续接会话。

PSM 应在后续对账中发现变化。

### 测试六：会话删除

会话确认删除后，Router 仍可说明历史任务曾经存在，但不能继续派发到失效会话。

### 测试七：项目重建

删除旧 `aaa` 后重新创建同名项目。

系统不能未经验证就继承旧项目的全部关联。

### 测试八：用户纠正

Router 匹配错误。

用户指出正确项目和会话。

系统应保存纠正，并在下次优先使用正确关联。

### 测试九：同步异常

索引过程中服务重启或数据库写入失败。

恢复后可以继续同步，不丢失水位、不产生重复记录。

### 测试十：现有功能回归

PSM 启用或关闭，都不能破坏现有 Router、Worker、Web、微信、审批和事件驱动功能。

### 最终判断标准

**PSM 的成功，不是建立了多少索引或存储了多少条记忆，而是 Router 能否真正理解用户所说的工作事项，并准确定位到过去的项目、会话和相关任务。**

它应该随着使用逐渐熟悉工作环境。

用户不需要反复解释项目名称、历史会话和任务位置。

PSM 应在后台自动同步，在交互中智能增强，在用户纠正后持续改进。

**让 Router 逐渐拥有对整个 Codex 工作环境的长期认知，而不是每次都像第一次使用这些项目一样重新查找。**
