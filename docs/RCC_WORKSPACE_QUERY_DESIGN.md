# RCC 补充设计：Workspace Read-only Queries（工作环境只读查询）

## 1. 背景与现象

codex-cli-web 已实现 Router/Worker、RCC 双模式、渠道焦点、可靠控制队列、PSM 与微信 iLink。任务模式的初衷是：实际业务工作交给 Worker，Router 不替 Worker 分析、开发或记忆业务细节。

真实微信使用出现：用户发送「请列出当前的所有项目」，系统最初要求指定目标；该句已被针对性修复。随后「简短介绍一下每个项目」仍要求指定完整项目或会话，无法顺畅回答。截图中项目列表可返回 11 项，但介绍请求再次被错误归入“必须绑定单一 Worker 的业务消息”。这说明单句白名单不足以覆盖对已有工作环境的自然查询。

本次仅补齐 Router 的**只读工作环境查询**能力，不重构 RCC、不引入 Agent、不增加 Router 长期记忆，也不改变任务模式的核心派发承诺。

## 2. 核心目标

在任务模式下，Router 能利用现有项目目录、PSM、会话与任务记录，回答已有工作环境的事实性问题；用户要求新的代码检查、项目分析、实现、测试、修改等实际工作时，仍交给 Worker。

区分的是**只读查询已有事实**与**请求产生新的业务工作**，不是重新判断用户“是否值得派发”。

- 「有哪些项目」「每个项目做什么」「哪些项目最近活跃」「USB 掉线任务在哪个会话」「有哪些任务等待审批」→ Router 查询已有事实后直接答复。
- 「检查 certbase 的代码架构」「分析所有项目的安全问题」「验证网络配置是否正确」「修改 IPv4」→ 派发 Worker。
- 「介绍一下 certbase」→ 优先已有项目描述/PSM；不启动 Worker 读取代码进行新分析。
- 「介绍项目并检查其代码结构」→ 识别混合请求：只读部分可先答，检查部分必须经过目标确认与可靠派发；不默默省略后半部分。

## 3. 系统职责与安全边界

Router：聊天、模式控制、系统信息只读查询、目标定位、转接、控制、反馈。Worker：新的业务分析与执行。PSM：项目/会话/任务主题的历史索引，**不是**实时事实或业务执行器。

- 只读查询不得创建 dispatch、command、Worker Turn，不得改变 mode、channel focus、审批状态、PSM 用户确认关联或 RCC 指令队列。
- 只读工具返回的元数据必须遵循现有项目授权、PSM 可见性及数据脱敏规则。未经授权的项目不能因批量概览泄露历史片段、任务内容或隐含命中数量。
- 项目简介必须区分：已确认描述、历史会话主题推断、信息不足；不得把推断写成确定项目用途。
- 项目数量、任务状态等动态数据从当前服务端事实读取；PSM 的历史索引可能延迟，需在必要时标明时间/来源。
- 不允许仅凭 Router 模型输出声称查询已完成。不得使用查询作为绕过任务模式、授权或 Worker 审批的路径。

## 4. 请求路由：建议统一分类，而非关键词堆砌

将任务模式入站请求按操作语义区分：

1. **System Control**：切换模式/焦点、停止/取消、审批、待办答复；走现有控制通道，优先级最高。
2. **Workspace Read**：只读查询已有项目、会话、PSM 描述、任务列表、状态、历史关联、活动概览；Router 直接调用受限只读工具并汇总。
3. **Worker Work**：新的项目业务分析、检查、测试、开发、变更或任务补充；遵循 RCC 目标解析与可靠投递。
4. **Ambiguous / Mixed**：目标或操作含义不明确时简短澄清；混合请求拆分后分别按各自权限执行。

不要将“项目”或“介绍”作为唯一判断依据。识别应结合句子中的**操作对象和要求的证据来源**：只要能从已有授权记录回答，就属于 Workspace Read；需要新的业务观察/分析，则属于 Worker Work。模型可以辅助理解复杂自然语言，但服务端最终必须限制可调用工具及操作类型。无法可靠判断时只问一个关键澄清问题，不要默认创建 Worker，也不要无限要求绑定单一目标。

优先复用当前 service.js 的任务模式分流、matching.js、已有 Router 动态工具与 PSM 工具；不要建立新的平行路由框架。若需要新增工具，优先增加**一个受限的批量只读查询能力**或扩展现有工具分页/批量参数，而不是逐个自然语言句式新增特判。

## 5. 工作环境查询能力与数据来源

### 5.1 项目目录

- 列出当前**有权展示**的项目，显示名称与可核实状态。
- 支持单项目与全项目概览；多项目查询不要求单一焦点。
- 分页或分批读取，不能受普通“候选前 N 个”“每项目最近三页”的 UI 搜索限制而误称全部。
- 明确区分“已登记项目”“可发现但未授权项目”与“历史索引中的项目”，按现有权限边界展示。

### 5.2 项目简介

建议使用统一的只读 `ProjectOverview` 投影（名称为设计概念，具体实现可复用现有结构）：

- `projectId`、可显示名称。
- `description`：已确认项目描述优先。
- `descriptionSource`：confirmed / indexed_history / unavailable。
- `topics`：最多 2–3 个有证据的历史主题，可选。
- `lastActivity`：有来源才展示。
- `indexFreshness`：必要时展示索引更新情况。

项目描述来源顺序：现有明确描述/用户确认的 PSM → PSM 项目语义条目 → 有证据的历史会话主题 → “暂无可靠描述”。不要通过项目目录名或模型常识编造用途。没有描述不等于失败，更不需要自动派发 Worker。

### 5.3 任务与会话概览

支持任务列表、执行中/等待审批/完成/失败、最近活动、当前焦点、任务与项目的关联。使用 Dispatcher/Store/Hub 的权威状态，不能用 PSM 代替实时任务状态。跨项目聚合时每项附简短项目归属，必要时分页。

### 5.4 历史定位

例如「USB 掉线任务在哪」使用 PSM 查找并引用原始证据；可以返回候选，不必创建 Worker。对多义候选简洁列出差异。只读查询不能自动更改用户确认关联。

## 6. 交互与输出规范

微信默认简洁：

用户：「简短介绍一下每个项目」

示例：

```
目前可查看 4 个项目：
1. codex-cli-web：Codex 工作台，包含 Router 和微信交互。
2. certbase：历史记录涉及证书相关功能。
3. aaa：历史记录涉及 USB 掉线排查。
4. bbb：暂无可靠项目简介。

这些介绍来自已有项目资料和历史记录，没有重新检查代码。
```

以上仅为示例，实际内容必须来自授权数据；不能照抄示例作为事实。

- 用户要求“简短”时每项目一行；数量多时优先分批并明确总数、已展示数、继续查看方式。
- 无资料时如实说明；历史推断使用“历史记录涉及……”而非“该项目就是……”。
- 不输出内部 Thread/Dispatch ID，除非用户要求排障。
- 任务模式的系统查询不触发模式切换，也不改变渠道焦点。
- Web 和微信使用同一事实查询路径，展示可按渠道适配。

## 7. 实施建议

### P0：审查与修正路由边界

1. 从截图场景追踪任务模式入站到 `routeContinuation()` / 目标匹配 / `askTarget` 的实际调用链。
2. 找到当前「列出项目」特判及导致「介绍项目」被派发定位的条件。
3. 提取统一 Workspace Read 判定与只读工具权限边界；将项目列表、项目简介、任务状态、历史定位纳入同一机制。
4. 保持现有 RCC 任务模式直接派发路径、Worker 控制队列和聊天模式行为不变。

### P1：批量项目简介与多项目概览

1. 复用现有 PSM / 项目元数据构建受权限过滤的项目简介。
2. 支持单个、全部、部分项目；处理分页、无描述、索引延迟和撤权。
3. 对多项目查询禁止强制单一焦点。
4. 对混合请求按只读与 Worker 工作分别处理，不擅自执行新业务。

### P2：交互、回归和真实渠道验收

1. 微信/Web 输出简洁、来源明确，符合 RIP 人格与表达策略。
2. 真实项目和无意义名称项目都能查询。
3. 验证无新增 Worker、无新 dispatch、无 mode/focus 改动。
4. 保持审批、RCC 补充指令、PSM、通知和多 Worker 并行正常。

## 8. 验收用例（必须包含）

| 输入（任务模式） | 期望 |
|---|---|
| 请列出当前所有项目 | 返回可见项目列表，不派发、不改变焦点 |
| 简短介绍一下每个项目 | 批量已有信息简介，无需选单一会话 |
| 介绍一下 certbase | 现有证据简介，信息不足时明确说明 |
| aaa 是做什么的 | 能使用 PSM 历史证据，不能凭名字编造 |
| 哪些项目最近比较活跃 | 读取已有活动记录，标明口径，不派发 |
| 现在有哪些任务正在执行 | 查询真实状态，不派发 |
| USB 掉线那个任务在哪个会话 | PSM 定位，不启动 Worker |
| 分析 certbase 的代码架构是否合理 | 交给 Worker，不由 Router 自行新分析 |
| 检查所有项目有没有安全问题 | 进入多目标任务确认/派发，不当作只读查询 |
| 简单介绍 certbase 并检查代码架构 | 只读介绍 + 对检查部分按 RCC 派发或确认 |
| 当前焦点是 A，查询 B 的简介 | 仍保持焦点 A |
| 无权限项目包含历史敏感片段 | 不泄露正文、片段、主题或数量 |
| PSM 索引尚未完成 | 返回可核实的现有信息并提示不足，不强制派发 |
| 微信同一请求重复送达 | 只读请求不会产生副作用；回复不异常重复 |

补充边界测试：同义改写、反问句、口语表达、无意义项目名、多项目超过一页、撤权并发、聊天/任务模式切换、用户主动指定 Worker 进行重新分析。所有只读场景断言 dispatch/command/Worker Turn 数量不增加，焦点和模式 revision 不变；所有实际工作场景仍经 RCC 可靠队列。

## 9. 必须避免

- 不要再为「介绍所有项目」单独新增一个中文关键词 if 分支。
- 不要把任务模式改回“模型随意决定是否派发”。
- 不要让 Router 为了回答简介去读取并分析项目源码。
- 不要引入新的 Router 长期记忆、Agent 或向量库。
- 不要在查询失败时默认派发 Worker。
- 不要把 PSM 的历史索引当作实时 Worker 状态。
- 不要让跨项目概览改变当前焦点。
- 不要泄露未授权项目的正文和关联。

## 10. Codex 交付要求

本轮先只读审查并提交实施计划，不直接修改源码。请交付：

1. 截图对应失败路径与已有“列项目”特判的具体代码位置。
2. 现有只读工具和 PSM 能力盘点，指出数据不足之处。
3. 请求分类与服务端强制边界的设计，解释为何不会削弱任务模式。
4. 多项目简介的证据优先级、权限、分页和来源标记方案。
5. 逐文件改动计划，优先最小改动。
6. 自动化与真实微信/Web 验收方案。
7. 风险、兼容性、未验证协议假设。

计划确认后再实施；不要把单元测试通过当作真实渠道验收。

## 11. 最终成功标准

任务模式下，Router 能自然回答「我有哪些项目、它们分别做什么、最近哪些任务在运行」等**已有系统事实**；同时对「检查、分析、修改、验证」等**新的项目工作**仍可靠派发给 Worker。整个过程无需为跨项目只读查询选一个 Worker，不改变焦点，不产生虚假事实，也不削弱 RCC 的任务模式规则。
