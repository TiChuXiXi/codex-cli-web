# codex-cli-web：Router 统一交互体验升级（RIX）需求与实施方案

## 一、项目背景

### 1. 现有系统

codex-cli-web 最初是一个基于 Codex App Server 的独立 Web 工作台，具备项目、会话、工具审批、终端、Git 和文件管理等能力。

随后参考 DeepSeek Harness Super Agent 的 Router / Worker 架构，实现了 Router 统一智能入口。

Router 的核心职责是：

- 理解用户自然语言需求。
- 自动寻找相关项目和历史 Worker 会话。
- 创建、续接和调度 Worker。
- 处理 Worker 的执行状态、审批、决策及结果反馈。
- 通过 Project & Session Memory（PSM）理解项目与会话历史。
- 通过 Web 和个人微信 iLink 与用户交互。

目前 Router、PSM 和微信 iLink 已经具备基本运行能力，简单通信和任务测试已经通过。

但是，实际微信使用中仍然存在明显的交互问题。

### 2. 当前遇到的问题

**问题一：微信无法完成某些会话选择和确认。**

Router 找到候选项目或会话后，有时要求用户必须到 Web 页面点击确认卡。

用户在微信回复「确定」「第二个」时，系统无法直接完成原有待办。

而且候选信息包含大量内部任务描述、文件路径和历史内容，消息非常冗长。

**问题二：Worker 审批通知有时缺少详情。**

有时微信只显示「需要审批」以及项目和会话 ID，没有具体操作。

另一些情况下又能够正确显示命令、目录、原因和选项。

这说明审批详情获取、待办关联或消息格式化可能存在不一致。

**问题三：Router 处理期间微信长时间没有响应。**

用户发送消息后，Router 可能需要检索 PSM、选择会话、调用工具和派发 Worker。

在 Router 产生最终输出前，微信没有任何反馈，用户不知道消息是否已经收到、是否正在处理或是否发生异常。

**问题四：Router 的语言过于机械化。**

微信中经常出现 Worker、Thread、任务编号、内部路径和技术状态等描述。

回复更像后台日志或工单通知，而不是一个自然交流的个人智能管家。

**问题五：Web 与微信的交互表现尚未完全统一。**

系统虽然已经有待办队列，但仍存在某些交互只能在 Web 完成、微信展示不完整、状态同步不及时或通知重复等问题。

---

## 二、为什么要进行这次升级？

Router 的设计初衷是：

**将管理多个 Codex 项目和 Worker 会话的工作，从用户身上转移到 Router 身上。**

用户只需要用自然语言描述需求。

Router 负责查找项目、选择会话、安排任务、处理执行过程，并在需要用户介入或任务完成时反馈。

微信 iLink 的设计初衷，则是让用户离开电脑后，仍然能够通过个人微信使用完整的 Router 能力。

但如果微信中仍然需要用户打开 Web 选择会话、查看审批或判断任务状态，那么微信只是一个不完整的通知工具。

如果每次任务反馈都充满内部 ID、执行日志和复杂术语，那么 Router 虽然在技术上完成了任务调度，却没有真正减少用户的理解成本。

因此，本次升级的目的不是增加更多工具，而是：

**让 Router 从一个能够远程操作的任务调度系统，转变为一个真正自然、可靠、能够独立完成交互闭环的个人工作管家。**

---

## 三、最终目标

用户无论通过 Web 还是微信，都能够与同一个 Router 自然交流。

对于普通任务：

用户只需描述需求，Router 主动完成项目与会话定位、任务派发及结果反馈。

对于不确定的任务：

Router 使用 PSM 和历史记录寻找候选，只向用户展示少量必要信息，用户可以通过自然语言或编号选择。

对于需要审批或决策的任务：

Router 将完整请求展示给用户，用户可以直接在当前渠道回答，系统将响应准确传回原 Worker。

对于耗时操作：

Router 应及时反馈真实进度，让用户知道消息已被接收、任务正在处理或已经交给 Worker。

对于任务完成：

Router 用自然、简洁的语言总结结果，而不是输出内部状态和任务编号。

**最终用户原则上不需要主动进入 Worker 会话，也不需要理解 Router、Worker、Thread、Dispatch 等内部技术概念。**

---

## 四、本轮开发范围与边界

本轮只优化 Router 的统一交互体验。

优先复用现有：

- Router Service。
- Router 动态工具。
- Router Dispatcher。
- Worker Hub。
- EventBus。
- Router Wake Scheduler。
- 微信 iLink Channel。
- 微信消息收件箱和发送队列。
- 统一待办队列。
- PSM 检索和记忆工具。

不要重新实现 Router / Worker 架构。

不要重新开发微信通信协议。

不要引入新的大模型或独立 Agent。

不要重新设计 PSM 数据库。

不要因为增加人格规则而扩大 Router 的文件或命令执行权限。

# 五、功能需求一：跨渠道统一待办交互

## 1. 目标

所有需要用户参与的 Router / Worker 交互，都应该能够通过 Web 或微信完成。

不能再出现：

「请到 Web 页面点击确认，微信无法操作。」

## 2. 统一待办类型

至少支持：

| 类型 | 示例 |
|---|---|
| 项目选择 | 选择目标项目 |
| 会话选择 | 选择需要续接的 Worker |
| Router 澄清 | 询问用户真正想处理哪个任务 |
| 原生工具审批 | 执行命令、文件操作、权限申请 |
| 原生用户输入 | Codex requestUserInput |
| 业务决策 | 选择方案 A 或 B |
| 高风险操作确认 | 推送代码、删除文件、部署等 |

不同待办可以有不同的处理方式，但必须共用稳定的待办身份和状态管理。

## 3. 微信候选选择

例如用户说：

「继续昨天那个 Web 界面任务。」

如果 Router 找到两个候选，微信应显示：

```text
找到两个可能的会话，你说的是哪个？

1. Web 界面优化
   最近在调整聊天区布局

2. Router 开发
   最近在完善 PSM 和记忆检索

回复 1 或 2 就行。
```

不要输出整个会话的原始任务描述。

不要默认展示长文件路径、Thread ID 或完整历史提示词。

用户应能够回复：

- `1`
- `第二个`
- `Web 界面那个`
- `选 Router 开发`
- `都不是`

对于能够唯一匹配的回复，系统应直接完成选择。

存在歧义时才继续询问。

## 4. 微信自然语言确认

现有确认卡可能要求精确的序号或 Web 点击。

本次需要增加统一的响应解析。

但不能简单通过关键词判断所有待办。

建议：

1. 先识别当前用户是否存在有效待办。
2. 判断消息是否明确引用某个待办。
3. 解析编号、候选名称或自然语言表达。
4. 验证目标是否唯一。
5. 唯一且有效时调用原有确认接口。
6. 不明确时请求澄清。
7. 不属于待办回复时，按普通 Router 消息处理。

不得将用户随口说的「可以」「继续」错误关联到其他审批请求。

## 5. 多待办处理

当存在多个待办时：

- 每个待办有稳定 ID。
- 每个待办有明确状态。
- 微信展示可理解的短编号。
- 用户可以指定某项待办。
- 不能将短编号永久绑定到某个 Worker。
- 待办完成、过期或取消后，旧回复不能再次执行。
- Web 与微信操作同一个待办时，只能有一次有效提交。

建议继续使用现有待办队列，不开发第二套交互状态机。

# 六、功能需求二：Worker 审批详情完整展示

## 1. 目标

任何通过微信请求用户审批的操作，都必须尽可能展示完整、真实、可判断的信息。

不能只显示：

```text
需要审批
codex-cli-web
255dcb2e
```

## 2. 审批消息规范

例如：

```text
【需要你确认】

项目：Codex Web
操作：执行命令
命令：npm run build
目录：/root/project/codex-cli-web

用途：验证本次修改能否正常构建。

1. 允许本次
2. 拒绝
```

对于文件修改、网络访问、权限提升等审批，应展示相应的实际操作内容。

不能把所有审批都格式化成「执行命令」。

## 3. 审批数据来源

优先使用 Codex App Server 原生审批请求。

需要检查：

- 审批事件是否包含完整参数。
- 是否需要根据 requestId 再次读取详情。
- 不同审批类型是否具有不同字段。
- 是否存在事件与详情到达时间不一致。
- 微信通知与 Web 审批卡是否读取相同数据源。
- 是否存在先发送简略通知、后续详情没有补发的情况。

## 4. 审批发送策略

如果收到审批事件时详情尚未完整：

- 先尝试短时间补查。
- 在合理时间内获取详情后再发送。
- 不应立即发送一个只有 ID 的审批通知。
- 若无法获取关键操作信息，明确提示详情不可用。
- 不允许在详情不完整时通过微信盲目批准。

## 5. 审批回传

用户在微信回复有效选项后：

1. 验证待办仍然有效。
2. 验证对应原生审批请求仍然存在。
3. 使用原有 Hub 审批接口响应。
4. 更新待办状态。
5. 同步 Web 和微信。
6. Worker 继续执行。

Router 模型不得代替用户作出原生工具审批决定。

---

# 七、功能需求三：微信处理中反馈与进度感知

## 1. 目标

用户向微信发送消息后，不应长时间完全没有反馈。

但也不能每条消息都立即发送「收到」，制造大量无意义通知。

## 2. 建议的响应策略

建议初始参数：

| 条件 | 行为 |
|---|---|
| 3 秒内完成 | 直接回复结果 |
| 超过 3 秒 | 发送一次简短处理中提示 |
| 超过 15 秒 | 有实际阶段变化时发送进度 |
| Router 已派发 Worker | 告知任务已安排 |
| Worker 长时间执行 | 不持续刷屏 |
| Worker 完成 | 主动发送结果 |
| Worker 需要用户参与 | 及时发送待办 |

这些时间应可配置，不能写死在业务逻辑中。

## 3. 状态来源

处理中提示应由服务端真实状态驱动。

例如：

- 消息已进入 Router 队列。
- Router 已开始处理。
- PSM 检索正在执行。
- Router 正在匹配项目或会话。
- Worker 已接受任务。
- Worker 正在执行。
- Worker 等待审批。
- Worker 已完成。

不能根据时间流逝凭空编造执行进展。

## 4. 消息表达

建议：

- 已接收但尚未开始：「收到，我稍后处理。」
- 正在检索：「我查一下之前的记录。」
- 已找到目标：「找到了，正在安排。」
- 已派发：「已经交给对应的开发会话了，完成后告诉你。」
- 等待审批：「有一步操作需要你确认。」
- 已完成：「这轮工作结束了，结果是……」

以上只是表达示例，不要求逐字重复。

## 5. 反馈去重

需要防止：

- 处理中消息晚于最终结果到达。
- 同一任务重复发送「已安排」。
- Worker 完成通知与 Router 总结重复发送。
- Web 和微信同时操作造成重复通知。
- 旧任务的进度消息混入新任务。

建议通过 requestId、dispatchId 和通知阶段建立幂等键。

对已经完成的请求，不应再发送过期的处理中提示。

## 6. 长任务体验

对于 Worker 执行 20～60 分钟的任务：

- 不需要每隔几分钟发送一次固定状态。
- 用户主动询问时，应能查询真实进度。
- 有重要阶段变化时可以主动通知。
- 需要用户介入时必须及时通知。
- 完成后应主动汇报。

本轮不需要开发复杂的进度百分比预测。

# 八、功能需求四：Router 身份与人格

## 1. 身份定位

Router 是用户的统一智能工作管家。

它熟悉项目和会话历史，能够理解用户意图、协调 Worker、处理交互和反馈结果。

它不是普通的聊天机器人，也不是机械的任务转发器。

## 2. 人格要求

建议默认人格：

- 专业、可靠。
- 温和、自然。
- 简洁、干练。
- 适度亲切。
- 偶尔轻松，但不过度卖萌。
- 不频繁称呼用户。
- 不使用固定夸张开场白。
- 不表现出虚假的情绪或依赖关系。

整体感觉应接近一个熟悉工作环境、做事利落的私人工作助手。

## 3. 身份配置

建议允许配置：

- 助手显示名称。
- 助手自称。
- 人格描述。
- 回复简洁程度。
- 语言风格。
- 微信专用表达规则。

产品内部模块仍然可以叫 Router。

展示名称与内部技术名称分离。

不要因为修改助手昵称而重命名 Router 服务、数据库表或接口。

## 4. 人格与权限分离

人格规则只能影响语言表达和交互方式。

不能改变：

- Router 工具权限。
- Worker 原有执行权限。
- 审批策略。
- 项目授权。
- PSM 证据约束。
- 高风险操作确认规则。

---

# 九、功能需求五：微信专用消息表达规则

## 1. 基本原则

微信不是终端日志窗口。

用户不应该在普通消息中频繁看到：

- Worker。
- Thread。
- Dispatch。
- requestId。
- 内部任务编号。
- 完整工作目录。
- 大段工具调用输出。
- 原始 JSON。

只有在用户要求技术详情、排查问题或审批需要时才展示相关信息。

## 2. 消息长度

建议：

- 普通状态：1～2 句话。
- 任务结果：2～5 句话。
- 候选选择：最多优先展示 3～4 项。
- 审批请求：保留必要完整操作内容，不受普通简洁规则限制。
- 长技术报告：先发摘要，必要时提供进一步查看方式。

## 3. 通知自然化

旧方式：

「Worker task_7831 completed, status=success。」

建议：

「刚才那个 Web 界面任务已经完成这一轮修改，构建和相关测试都通过了。」

注意：只有实际执行了构建和测试且结果通过，才能这样描述。

旧方式：

「Dispatch submitted to thread 255dcb2e。」

建议：

「已经安排给原来的开发会话了，完成后我会告诉你。」

## 4. 区分模型回复与系统通知

模型负责：

- 理解用户意图。
- 生成自然语言答复。
- 总结 Worker 结果。
- 解释候选差异。
- 提供必要的业务说明。

服务端负责：

- 待办编号。
- 审批选项。
- 真实状态。
- 通知时机。
- 消息去重。
- 跨渠道同步。

不要为了润色每条系统通知而额外调用模型。

优先使用可配置的消息模板。

# 十、功能需求六：PSM 与自然交互结合

PSM 已经具备项目、会话和历史任务索引能力。

本轮不重建 PSM，但需要让它更好地服务自然交互。

例如：

用户说：

「看看 USB 掉线的问题。」

Router 应优先利用 PSM 查找已确认关联和相关历史。

如果找到多个候选，应提供简洁、容易区分的描述。

用户确认后，应使用现有 PSM 工具保存可靠关联。

以后再提到该任务，减少重复确认。

**不能为了展示候选而把完整历史任务提示词复制到微信。**

---

# 十一、跨渠道状态一致性

Web 和微信应共享：

- 当前 Router 主会话。
- 项目和会话选择待办。
- Worker 审批待办。
- Worker 用户输入待办。
- Router 澄清状态。
- Worker 执行结果。
- PSM 关联与用户纠正。

用户在微信完成待办后，Web 应同步更新。

用户在 Web 处理待办后，微信旧选项不得重复执行。

同一个请求只能有一次有效处理结果。

微信断线或重连后，应从持久化待办状态恢复，而不是重新创建重复待办。

---

# 十二、技术实施建议

请先检查当前真实源码，再确定文件改动。

建议从以下逻辑模块入手：

### 1. Interaction Service

统一处理候选、确认、审批、用户输入和业务决策。

优先复用现有待办队列。

### 2. WeChat Presentation

负责微信消息格式化、候选列表、审批详情和自然化模板。

不得承担 Router 的智能决策职责。

### 3. Response Lifecycle

负责消息受理、处理中反馈、阶段更新、最终回复和去重。

建议与微信收件箱、发送队列和 Router 执行状态关联。

### 4. Router Identity

管理助手名称、人格和表达规则。

尽量复用当前 Router 提示词配置体系。

### 5. Cross-channel State

确保 Web 与微信共享待办和 Router 会话状态。

以上只是职责划分，不要求增加五个独立服务。

应尽可能复用现有代码，避免重复状态机和数据表。

---

# 十三、实施顺序

## 阶段一：源码审查与问题定位

先针对三张实际微信截图还原完整调用链。

重点定位：

- 为什么微信不能确认某些会话候选？
- 为什么部分审批缺少操作详情？
- 为什么 Router 开始处理后微信没有及时反馈？
- 当前有哪些通知重复或状态同步问题？

形成具体问题清单。

## 阶段二：统一待办交互

优先解决微信会话选择、Router 澄清、Worker 审批和用户输入。

保证用户不必打开 Web。

## 阶段三：审批详情修复

统一审批数据源、格式化和响应流程。

覆盖不同审批类型、详情延迟到达及过期状态。

## 阶段四：处理中反馈

增加消息生命周期状态、延迟反馈、阶段通知及去重。

不阻塞 Router 或 iLink 长轮询。

## 阶段五：人格与表达规范

增加 Router 身份配置和微信专用消息规则。

让普通通知更加自然、简洁。

## 阶段六：跨渠道与真实任务验证

通过 Web、微信和真实 Worker 任务测试完整闭环。

# 十四、验收标准

## 测试一：微信会话选择

用户通过微信要求继续一个存在两个候选的历史任务。

系统展示两个简洁候选。

用户回复「第二个」。

Router 直接续接正确会话，不要求打开 Web。

## 测试二：自然语言选择

用户回复「Web 界面那个」。

系统正确识别候选并继续。

## 测试三：审批详情

Worker 请求执行命令。

微信展示完整命令、目录、原因和允许/拒绝选项。

不出现只有 ID 的审批消息。

## 测试四：审批回传

用户回复「1」。

系统准确响应原生审批请求，Worker 继续执行。

## 测试五：多审批

两个 Worker 同时请求审批。

用户回复模糊的「允许」。

系统不能猜测目标，应要求明确选择。

## 测试六：处理中反馈

Router 处理耗时超过设定阈值。

微信在合理时间内收到真实的处理中提示。

Router 最终完成后，正常发送结果。

## 测试七：短消息

Router 在 3 秒内完成普通问答。

微信只收到最终回复，不额外收到「收到」通知。

## 测试八：长任务

Worker 运行 20 分钟。

微信不会持续刷屏。

任务完成后收到结果。

## 测试九：通知去重

Worker 完成后，系统不会同时发送重复的原始完成通知和 Router 总结。

## 测试十：跨渠道状态同步

用户在 Web 完成审批，微信旧待办立即失效。

反向操作同样成立。

## 测试十一：PSM 候选

项目名称和会话标题都没有明确业务含义。

Router 使用 PSM 找到相关历史内容，并在微信展示简洁候选。

## 测试十二：人格一致性

Web 与微信中的 Router 保持相同身份和基本语言风格。

微信消息更简洁，但不改变事实和执行结果。

## 测试十三：异常恢复

Node 服务或微信连接短暂中断后，待办、回复和通知能够恢复，不重复审批或派发。

## 测试十四：原有功能回归

现有 Router、Worker、PSM、Web、微信 iLink、审批和事件驱动功能均保持正常。

# 十五、必须避免的设计偏差

1. 不要为了微信交互重新开发一套 Router。
2. 不要要求用户频繁进入 Web 才能完成微信中的正常操作。
3. 不要把完整任务历史和内部对象直接输出给用户。
4. 不要用提示词代替原生审批数据校验。
5. 不要让模型自行批准工具请求。
6. 不要把所有微信消息都当作普通 Router Prompt。
7. 不要用固定时间模拟虚假的任务进度。
8. 不要每条消息都发送机械的「收到」。
9. 不要让人格规则覆盖真实状态和安全策略。
10. 不要引入复杂消息中台、独立 Agent 或新的任务调度框架。

## 最终判断标准

**这次升级是否成功，不取决于增加了多少配置或模块，而取决于用户能否真正只通过微信自然地使用 Router。**

用户应该能够：

- 自然描述任务。
- 在微信完成候选选择。
- 直接处理审批和决策。
- 及时了解任务是否正在处理。
- 接收简洁、准确的结果。
- 不必理解内部 Worker 和任务编号。
- 不必为了正常交互返回 Web。

**Router 应该像一个熟悉工作环境、能够替用户协调事务的可靠管家，而不是一个通过微信发送技术日志的任务调度程序。**
